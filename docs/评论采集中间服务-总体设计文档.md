## 1. 项目概述

### 1.1 目标

构建一个**多平台、多供应商的评论采集中间服务**，屏蔽底层数据供应商（官方 API、第三方服务、自研爬虫）在成本、速率、稳定性上的差异，
对外提供统一的任务提交、调度、执行与结果返回能力。

### 1.2 范围

**本期包含**
- 多平台评论采集：`weibo`、`douyin`、`xhs`（小红书）、`bilibili`、`toutiao`
- 主任务/子任务两级模型；同步即时返回 + 异步任务两种模式
- 供应商路由、限流、重试与故障切换
- 优先调度与防饥饿
- 任务持久化与重启恢复

**本期不含（列入 §17 后续阶段）**
- 微信平台、互动指标更新、账号历史
- 管理后台 UI、接口鉴权、集群化部署
- 具体爬虫的反爬对抗（由各供应商实现类自行承担）

### 1.3 术语

| 术语 | 说明 |
|---|---|
| 平台 | `platformCode` ∈ {`weibo`, `douyin`, `xhs`, `bilibili`, `toutiao`} |
| 功能 | `featureCode`，本期仅 `comment` |
| 供应商 | 实现某平台某功能的数据提供方，由 `providerKey` 标识，**必须与 Spring Bean 名一致** |
| 主任务 | 一次完整采集请求，关联一个或多个链接 |
| 子任务 | 主任务按链接拆分的执行单元，是**调度的最小单位** |
| 即时返回（SYNC） | 同步等待执行完成并返回结果，不产生任务记录 |
| 任务模式（ASYNC） | 返回任务 ID，异步执行，调用方轮询 |
| 有效优先级 | `priority - agingCount × boost`，**数值越小越优先** |
| 熔断 | 供应商连续失败后暂时隔离，冷却后半开放行探测 |

**统一约定**

1. **一页一次调用**：`CommentProvider#fetchComments` 每次只取一页；翻页靠返回的
   `CommonEntity.haseMore` + `nextUrl`（游标/页码），调用方回填到 `request.extra` 后再次调用。
2. **入参**：`request.extra` 承载供应商参数（`cookie` / `mid` / `cursor` / `page` / `buffer` / `commentId` …），
   由 `TaskManagementService#parseExtra` 从任务的 `requestParams`(JSON) 解析而来。
3. **内容 ID 解析**：`ProviderUrls.resolveMid`（通用取链接最后一段）与 `WeiboUrlParser`
   （`WeiboTool.urlToMid` + uid 正则）负责从链接推导 `mid`，无需调用方额外传参。
4. **失败表达**：抛异常或返回 `status != STATUS_SUCCESS` 都算失败，二者都会被框架识别（见 §9.2）。
5. **内部重试**：每个供应商对单次 HTTP 调用内部重试 3 次（间隔 1s），
   与框架层的"供应商切换级重试"职责区分。

> ⚠️ **上游业务码必须校验**：中科天玑接口在业务失败时会返回 HTTP 200 +
> `{"code":500,"message":"获取评论信息失败, 请重试", ...}`。仅判断 `body.contains("comments")`
> 会把这种响应误判成"成功但无数据"，导致既不重试也不切换供应商。四个 Golaxy 供应商均已加 `code != 200 → 失败` 判断。

## 5. 数据模型

### 5.0 数据访问与命名约定（重要）

#### 5.0.1 数据访问：`MongoTemplate` + `auto-task-web` 的 DAO 风格 `[已实现]`

**决策：所有 MongoDB 访问统一走 `MongoTemplate`，写法对齐 `auto-task-web` 的 `dao` 包，不使用 Spring Data 的 `MongoRepository`。**

| 项 | 说明 |
|---|---|
| 数据源 | 单一数据源，由 Spring Boot 自动配置（`spring.data.mongodb.uri`）；**不再自定义多数据源**（原 C-10 已消除） |
| 包 | `com.sysj.collector.dao`（对应 `auto-task-web` 的 `com.sysj.auto.task.web.dao`） |
| 类 | `MasterTaskDao` / `SubTaskDao` / `PlatformFeatureConfigDao` / `UserTierConfigDao` / `SupplierStateDao` |
| 注解与注入 | `@Component` + `@Slf4j`；`@Resource private MongoTemplate mongoTemplate;`（与 auto-task-web 一致） |
| 方法风格 | 每个 DAO 自包含，`Query`/`Criteria`/`Update` **内联在方法体内**，不抽公共基类、不抽字段常量类 |
| 批量写入 | `saveAll` 先 `insertAll`，失败后逐条 `save` 兜底（照搬 auto-task-web 的写法） |
| 数据归属 | 数组元素的 `$` 位置更新（供应商健康/速率）下沉到 `PlatformFeatureConfigDao`，Service 层不持有 `MongoTemplate` |
| `_class` 字段 | 已通过 `MongoConfig` 关闭（`DefaultMongoTypeMapper(null)`），文档中不写入 `_class` |

**为什么不用 `MongoRepository`**

1. 派生查询无法承载后续调度所需的**原子抢占**（`findAndModify`）、`$` 数组元素更新、字段投影、批量 upsert；
2. Repository 与手写 `MongoTemplate` 若指向不同数据源，会出现"写到另一个库"的事故（原 C-10）；
3. 与 `auto-task-web` 保持同一种数据访问写法，跨项目阅读成本最低。

> 注：`auto-task-web` 的 DAO 里带 `stream`（流式导出）、`skip/limit`（分页）、`cleanOldData`（过期清理）等能力，
> 本项目的 `SubTaskDao` 也保留了 `streamByMasterTaskId` / `getSubTasksByMasterTaskId`（分页）供后续导出与查询接口使用。

#### 5.0.2 字段命名：落库下划线式，但**查询可用驼峰** `[已实现，实测]`

`application.properties` 配置了：

```properties
spring.data.mongodb.field-naming-strategy=org.springframework.data.mapping.model.SnakeCaseFieldNamingStrategy
```

因此**落库字段名是下划线式**（实测原始文档）：

```
platform_feature_config : platform_code / feature_code / feature_name / status / providers[].provider_key / is_healthy
master_task             : user_id / platform_code / total_links / create_time ...
sub_task                : master_task_id / aging_count / retry_count / max_retry ...
```

> ⚠️ **重要更正（2026-09-23 实测）**：此前认为"手写 `Criteria`/`Update` 必须写下划线名，写驼峰会静默匹配 0 条"是**误判**。
> `MongoTemplate` 在执行前会经 `QueryMapper` / `UpdateMapper` 按实体映射规则转换字段名，**驼峰与下划线两种写法都能命中**。
> 实测结果：
>
> | 写法 | 命中 |
> |---|---|
> | `Criteria.where("platformCode")`（驼峰） | 1 ✅ |
> | `Criteria.where("platform_code")`（下划线） | 1 ✅ |
> | `Criteria.where("providers.providerKey")`（驼峰嵌套） | 1 ✅ |
> | `Update.set("providers.$.isHealthy")`（驼峰 + `$`） | matched = 1 ✅ |
>
> 结论：**DAO 中统一写驼峰**（与 `auto-task-web` 一致，也与实体字段名一致，可读性更好）。
>
> **唯一例外**：`@CompoundIndex(def = "...")` 的字符串不经过映射器，必须直接写落库名 ——
> 已在 `PlatformFeatureConfig` 中写为 `{'platform_code': 1, 'feature_code': 1}`。
>
> 另：`updateProviderHealth` / `updateProviderRate` 现按 **`matchedCount`** 判定并返回，
> 未命中时打印 WARN（`modifiedCount` 在"值未变化"时也是 0，会误判）。

**映射的前提：字段必须声明在实体上** `[2026-09-23 实测补充，见 C-42]`

上面那句"驼峰会被自动映射"有一个**关键前提**：该名字能在实体元数据里找到对应属性。
若属性不存在，`MongoTemplate` **不会报错，而是把名字原样写入**：

| `Update.set(...)` 的参数 | 实体上是否有该属性 | 实际落库字段 |
|---|---|---|
| `effectiveQps` | 有 | `effective_qps` ✅ |
| `adaptiveDelayMs` | 有 | `adaptive_delay_ms` ✅ |
| `providers.$.isHealthy` | 有（`providers` + `isHealthy`） | `providers.$.is_healthy` ✅ |
| `notAProperty` | **没有** | `notAProperty` ❌ 原样写入 |

实测方式：用 `MongoMappingContext` + `SnakeCaseFieldNamingStrategy` + `UpdateMapper` 做纯映射断言（6/6 通过，不连 Mongo）。

> 踩坑经过：新增 `effective_qps` / `adaptive_delay_ms` 落库时，**忘了先在 `SupplierState` 上声明这两个字段**，
> 结果文档里出现了 `adaptiveDelayMs` / `effectiveQps` 两个驼峰字段，与相邻的下划线字段并存，
> 而且 `find` 回来也读不到。⇒ **新增落库字段时，先加实体属性，再写 DAO 更新语句。**

#### 5.5.1 为什么 `data_type` 索引必须带上 `insert_time` `[已实测]`

分页查询（`GET /api/tasks/{taskId}/comments?dataType=...`）是"等值过滤 + `insert_time` 倒序 + limit"。
若索引只到 `{task_id, data_type}`，排序键不在索引里，MongoDB 只能把匹配到的**全部**文档取回后在内存里排序。

5000 条样本、`{task_id:'T1', data_type:'wechat_comment'}` 取前 100 条的实测对比：

| 索引 | 执行计划 | keysExamined | docsExamined | 内存排序 |
|---|---|---|---|---|
| `{task_id, data_type}` | `SORT > FETCH > IXSCAN` | 166 | 166 | **是**（阻塞式） |
| `{task_id, data_type, insert_time:-1}` | `LIMIT > FETCH > IXSCAN` | 100 | 100 | 否 |

即将排序键并入索引后，计划从"扫描 → 内存排序 → 截断"变成"按索引有序取 100 条即停"。
数据量越大、命中越多，差距越显著 —— 这是 C-30 里唯一一个**实测能看出退化**的索引缺口。
旧的 `{task_id, data_type}` 是新索引的前缀，已被完全覆盖，脚本中会幂等删除。

### 5.6 状态机（统一，替代三份文档的三套枚举）

**主任务**

```
PENDING ──(开始调度)──> ACTIVE ──(全部子任务终态)──> COMPLETED
   │                       │
   └──(创建即失败)─────────┴──> FAILED
```
`PARTIAL_SUCCESS` 为可选终态（部分成功），本期 `[未实现]`。

**子任务**

```
PENDING ──抢占──> RUNNING ──> SUCCESS
   ▲                 │
   │                 ├──(失败, retry_count<max_retry)──> RETRYING ──> RUNNING
   │                 │
   ├──(切换供应商, 重置 retry_count)──────────────────────┘
   │                 │
   │                 └──(全部供应商耗尽 / 熔断)──> FAILED
   └──(misfire 重排 / 重启恢复)
```

**熔断器**（`[借鉴 B-15]`）

```
CLOSED ──(失败率>阈值 或 慢调用比例>阈值)──> OPEN ──(冷却期结束)──> HALF_OPEN
   ▲                                                                    │
   └────────────(探测成功)─────────────────────────────────────────────┤
                                                                        │
   OPEN <──────────────────(探测失败)───────────────────────────────────┘
```

## 6. 核心流程

### 6.1 任务创建（同步 / 异步）

```
POST /api/collect （SYNC）
 1. 参数校验（Bean Validation + 平台/功能存在性 + 链接格式）      [C-16]
 2. 解析用户等级 → 优先级、供应商偏好
 3. 路由：候选构建 → 能力过滤 → 健康/熔断过滤 → 阈值 → 流控
 4. 执行：ProviderInvocationPipeline
 5. 落库：CommentStore.saveAll（业务主键去重）
 6. 返回 CommentCollectResult
 ※ SYNC 不产生 master_task / sub_task 记录

POST /api/tasks （ASYNC）★重构
 1. 参数校验
 2. 创建 MasterTask(status=PENDING) 落库
 3. 按 links 拆分 SubTask(status=PENDING, next_execute_time=now) 批量落库
    · 幂等：唯一索引 (master_task_id, link)，重复提交捕获 DuplicateKey 后忽略  [B-13]
    · overflow_strategy 处理同 target 并发                              [B-02]
 4. MasterTask.status = ACTIVE
 5. 返回 taskId
 6. 【由 SubTaskScheduler 接管执行】← 当前完全缺失（C-13）
```

### 6.2 子任务调度循环 ★ 核心重构

```
SubTaskScheduler（固定间隔轮询，默认 200ms，可配）
 1. 查询候选：
    find({ status: "PENDING", next_execute_time: { $lte: now } })
      .sort({ effective_priority: 1, next_execute_time: 1 })     // 升序 = 优先级高者先
      .limit(batch_size)
 2. 逐个原子抢占（替代读改写，修正 C-32）：
    findAndModify(
      query : { _id: sid, status: "PENDING" },
      update: { $set: { status:"RUNNING", lock_owner: nodeId,
                        lock_expire_time: now+timeout, start_time: now } })
    → 返回 null 说明已被其他节点抢走，跳过
 3. 提交到 providerPool 执行（与调度线程池隔离）[B-06]
 4. 执行完成 → 原子回写 status/result_ref/comment_count/retry_count/cursor
 5. 子任务终态 → 触发主任务计数收敛（findAndModify $inc）
 6. 主任务全部终态 → status = COMPLETED / FAILED
```

**Aging（防饥饿）在此模型下自然生效**：`effective_priority` 在**查询时**计算并写回（或由定时任务批量刷新），
不再依赖 `PriorityBlockingQueue` 的堆重排 —— 一次性解决 C-08。

### 6.3 失败重试与供应商切换

```
1. 执行 fetchComments
2. 失败判定（★修正 C-06）：抛异常 或 status != STATUS_SUCCESS 均视为失败
3. retry_count++ 且 retry_count <= max_retry
   → status=RETRYING，next_execute_time = now + backoff(n)   [B-04]
   → backoff: FIXED = base
              EXPONENTIAL = min(base × 2^(n-1), retry_max_ms) + jitter
   → 重新入队（不阻塞线程）  [B-07]
4. retry_count > max_retry → attempted_providers += provider_key
   → 熔断器记录失败 [B-15]，status=PENDING，reset retry_count
   → 下次调度自动选下一个供应商
5. 所有候选耗尽 → status=FAILED，记 error_message
```

### 6.4 重启恢复与断点续采

```
ApplicationReadyEvent（异步执行，不阻塞启动）
 1. master_task.status IN (PENDING, ACTIVE) 的主任务
 2. 其下 sub_task.status IN (PENDING, RUNNING, RETRYING)
 3. RUNNING 且 lock_expire_time < now → 视为中断，重置：
      status=PENDING, lock_owner=null, next_execute_time=now
    ★ 不再重置 retry_count（保留退避进度）
 4. NEW：cursor / last_page 保留 → 从断点页继续  [B-24]
 5. 调度器自然接管，无需"重新提交请求"（修正 C-14）
```

## 7. 路由与调度设计

### 7.1 路由职责单一化 `[已实现]`

**原问题**：`DynamicProviderRouter.route()` 是死代码，`buildCandidates()` 与 `buildOrderedCandidates()` 逐行重复，
门面走的是"自己过滤 + 自己限流"的第二套逻辑，导致 `activation_threshold` 从未生效（C-17/C-18）。

**现状**：路由只保留**一个**入口（2026-09-23 完成，v2.5）：

```java
public record RouteContext(
        String platformCode, String featureCode,
        List<ProviderConfig> allProviders,      // 顺序不作为路由依据
        FeatureProviderConfig featurePreference, // 可 null
        String requiredProviderKey) {            // 非空 = 强制指定供应商
    static RouteContext of(platform, feature, allProviders, pref);
    static RouteContext specified(platform, feature, allProviders, requiredProviderKey);
}

List<ProviderConfig> select(RouteContext ctx)   // 唯一入口
```

内部顺序：

```
1. 指定供应商分支（requiredProviderKey 非空）→ 直接返回该供应商，跳过后续全部过滤；未配置则抛 CollectorException
2. 候选构建：providerOrder 内的按其给定顺序在前，其余按 priority 显式升序追加
3. 健康过滤：providers[].is_healthy == false 剔除
4. 激活阈值：pending < activation_threshold 时只保留候选首位
5. 返回有序候选（可能为空 → 调用方直接失败）
```

**为什么流控不在 `select()` 内**（与原设想的差异）：限流令牌必须按"真正要执行的那一刻"领取。
若在候选构建阶段就把所有候选的令牌领掉，未被使用的候选会白白消耗配额。
因此 `select()` 只决定"选谁、按什么顺序、够不够格"；门面在遍历候选、**执行前**调用
`tryAcquireProvider(platform, feature, key, ratePerSecond)` 领令牌。

**候选排序修正（C-17）**：排序改为显式 `Comparator.comparingInt(ProviderConfig::getPriority)`，
不再依赖 DB 数组的物理顺序；同 priority 时稳定排序保持 DB 顺序。

> 原先 `buildCandidates` 在无偏好时 `return allProviders;`，完全依赖写入时的顺序。
> 一旦有人手工在 MongoDB 里调整 `providers` 数组顺序，路由行为就会静默改变。

**指定供应商也走同一入口**：`request.specifiedProviderKey` 通过 `RouteContext.specified(...)` 进入 `select()`，
门面不再自建一份"从 providers 里找 key"的重复逻辑；语义保持"跳过健康/阈值"。

### 7.2 能力过滤 `[借鉴 B-26]` `[已实现]`

实现：`core/provider/` —— `Capability`（枚举）+ `@ProviderCapability`（注解）+ `ProviderCapabilityValidator`（启动校验）。

```java
enum Capability {
    COMMENT,        // 能采一级评论
    SUB_COMMENT,    // 能采二级评论/回复（支持 extra.commentId）
    CURSOR_PAGING,  // 游标翻页
    PAGE_PAGING,    // 页码/偏移翻页
    SYNC_SUPPORTED, // 支持即时返回（FR-18 一直无法判断的那一项）
    PROXY,          // 支持走代理（含代理失败自动直连）
    LOGIN_STATE     // 需要登录态/凭据
}
```

- **配置侧**：`platform_feature_config.providers[].capabilities`（字符串数组，大小写不敏感，未知值丢弃并告警）。
- **请求侧**：`CommentCollectRequest.requiredCapabilities`，要求候选**全部具备**（AND 语义）。
- **过滤位置**：健康/熔断过滤**之后**、激活阈值**之前** —— 健康是"能不能用"，能力是"合不合适"。
  放在阈值前是必要的：否则"能力过滤后只剩唯一候选"时，阈值会把它再砍掉，导致请求必然失败（用例 [9] 钉住）。
- **兼容性**：供应商未声明 `capabilities` 时**不因能力被过滤**，老配置无需改动即可继续工作。
- **失败可诊断**：候选为空时区分两种原因 —— "无候选满足所需能力 [X]；实际候选能力: k=[…]"
  vs "当前无可用供应商（全部被熔断隔离或运维下线）"，前者改请求/补配置，后者等恢复/修上游。

#### 7.2.1 启动期一致性校验 `[借鉴 B-30]` `[已实现]`

`ProviderCapabilityValidator` 在 `ApplicationReadyEvent` 时逐条比对**三个来源**：

1. DB 的 `provider_key` → 容器里有没有对应 Bean（没有则 **ERROR**）；
2. Bean 类上的 `@ProviderCapability` → 代码真实能力；
3. DB 的 `capabilities` → 配置声明。


### 7.6 优先级与防饥饿 `[已实现]`

#### 7.6.1 有效优先级

```
effectivePriority = deadlineForced ? 0
                                  : max(0, basePriority - agingBoost)

basePriority  = 用户等级 priority（ENTERPRISE 1 / VIP 10 / NORMAL 100；未配置等级 999）
agingBoost    = (等待秒数 / agingIntervalSeconds) × agingPriorityBoost     ← 阶梯递增
数值越小越优先
```

#### 7.6.2 Aging 与 deadline 保障 `[已实现]`

```
Aging 检查定时器（每 max(5, agingIntervalSeconds/3) 秒一次）：
  遍历队列快照，对每个等待中的任务：
    elapsedSeconds = now - enqueueTime
    if elapsedSeconds > maxWaitMinutes × 60 → forceHighestPriority()   // deadline 保障
    else agingBoost = (elapsedSeconds / agingIntervalSeconds) × boost
```

**关键实现点（这是修复 C-08 的核心）**：队列组件 `PriorityTaskQueue` 在**出队时才计算有效优先级**，
不使用 `PriorityBlockingQueue`。

> `PriorityBlockingQueue` 只在插入/删除时堆化：元素在队列里等待期间，即使优先级被 aging 提升，
> 堆内位置也不会变化 —— 防饥饿机制形同虚设。改为"出队时现算"后，aging 一改字段，下一次出队立刻生效。
>
> 代价是每次出队要扫一遍等待队列（O(n)），n 是"等待中的采集任务"数，量级远小于一次 HTTP 调用成本。
> 集群化后（P5）改用 `sub_task` 表按 `effective_priority` 排序查询，天然带索引。

#### 7.6.3 公平配额 `[已实现]` `[借鉴 B-01]`

组件：`core/scheduler/FairQuotaPolicy`（纯计算，无状态）+ 每消费者线程一份的 `ThreadLocal<FairRound>`。

```
每个消费轮次 = fairQuotaBatchSize 次取任务（默认 20）

轮次开始时：
  highCount = 队列中 effectivePriority < fairQuotaHighPriorityBound 的任务数
  lowSlots  = 0                                            若 total<=0 或 highCount<=0 或 highCount>=total
            = 0                                            若 highCount/total < fairQuotaThreshold
            = clamp(ceil(batchSize × fairQuotaRatio), 1, batchSize)   否则

轮次内每次取任务：
  若 lowSlots > 0：
      从"非高优先级"任务里取一个（pollIf）→ 成功则 lowSlots--、picksRemaining--
      取不到（队列里已无低优任务）→ lowSlots = 0，立刻转为正常取任务
  正常取任务：取当前 effectivePriority 最小的任务（阻塞 take）
```

**修正的两个缺陷（C-09）**：

| 原实现 | 现在 |
|---|---|
| "高优先级"硬编码 `priority < 500` | 来自配置 `collector.task.fair-quota-high-priority-bound` |
| `AtomicBoolean fairRoundActive` + `AtomicInteger fairRoundProcessed` **跨消费者线程共享**，互相干扰 | 每线程一份 `ThreadLocal<FairRound>`，互不影响 |
| 以"当前队列长度"当批次大小，语义含糊 | 固定轮次长度 `fair-quota-batch-size`，每轮预留 `ceil(batch×ratio)` 个名额 |
| 低优任务取不到时直接退出公平模式 | 同上，并且**不会**让高优先级挨饿（放弃预留即恢复正常调度） |

#### 7.6.4 相关配置

```properties

collector.task.aging-priority-boost=10
collector.task.max-wait-minutes=30
collector.task.fair-quota-ratio=0.3
collector.task.fair-quota-threshold=0.7
collector.task.fair-quota-high-priority-bound=500
collector.task.fair-quota-batch-size=20
```

启动时会打印一行确认参数已加载：

```

```

|---|---|
| 提升队列中某任务的优先级后再出队 | 该任务被优先取出（**旧的 PriorityBlockingQueue 实现此处会失败**） |

### 7.7 阈值分流 `[已实现]`

`activation_threshold` 在统一路由 `select()` 中生效：待处理数 `< threshold` 时只允许候选列表首位。

| 项 | 说明 |
|---|---|
| 计数来源 | `DynamicProviderRouter.pendingCountMap`（JVM 内存），键 `platformCode:featureCode` |
| 计数时机 | 门面在调用 `select()` **之前** `incrementPending()`，`finally` 中 `decrementPending()`；因此计数含当前任务本身 |
| 判定 | `threshold > 0 && healthy.size() > 1 && pending < threshold` → 截断为 `[首位]` |
| `threshold = 0` | 不限制，全部健康候选可用 |
| 日志 | 命中截断时打 `未达激活阈值，仅启用首位供应商: pending=… threshold=… key=…` |

**语义示例**（`user_tier_config` 种子数据）：

| 等级 | 微信/微博 `activation_threshold` | 效果 |
|---|---|---|
| `ENTERPRISE` | 0 | 全部候选可用：`weibo_official` 失败后自动切 `local_crawler` |
| `VIP` | 3 | 待处理 < 3 时只走 `weibo_official` |
| `NORMAL` | 10 | 待处理 < 10 时只走 `weibo_official` |

> 设计意图：低负载时只用首选的（通常更便宜/更稳的）供应商，避免为单个任务就去打备用供应商的配额；
> 负载升高后才把备用通道打开做分摊。

#### 7.7.1 阈值与熔断过滤的相互作用 `[已实测]`

阈值判断排在健康/熔断过滤**之后**，作用对象是**过滤后**的候选列表。由此得到一个必须显式写死的行为：

> **阈值管的是"负载分摊"，不是"可用性"。首选通道因熔断不可用时，会让位给下一个可用候选。**

| 场景（`threshold=5`、`pending=1`、候选 `[a, b]`） | 结果 |
|---|---|
| `a`、`b` 都健康 | `[a]` —— 低负载只用首选 |
| `a` 熔断、`b` 健康 | `[b]` —— **让位**，不是整体失败 |
| `a`、`b` 都熔断 | `[]` —— 门面返回"当前无可用供应商" |

**为什么这样定**：阈值是为**成本/配额分摊**而设的。若按"候选原始下标 `i>0` 一律跳过"的写法
（即 C-18 原实现），首选一旦熔断，备用也会被阈值挡住 → **首选故障直接放大成整体不可用**，
这恰好抹掉了多供应商的全部意义。反过来，若首选可用，备用在低负载下依然不会被使用，成本目标不受影响。

> 这是相对 C-18 原实现的一处**有意行为变更**，已由用例 [18] 钉住（§7.1.1 同一套验证）。

#### 7.7.2 验证方式 `[已实测]`

- 单元：`select()` 在 `threshold=3`、`pending=2→3` 时输出 `[a]→[a,b]`；阈值与熔断的组合见 §7.1.1 用例 [18]。
- **端到端对照**（同一链接、同一时刻，仅换用户等级；`weibo_official` 上游持续失败）：

```

  → 错误信息只含 {weibo_official=…}                    ← 阈值生效，只用首位
[ENTERPRISE] threshold=0
  → 错误信息含 {weibo_official=…, local_crawler=…}      ← 候选放开
```

## 8. 限流·熔断与降级设计

### 8.1 总体顺序 `[借鉴 B-19]` `[已实现]`

实际装配（`core/pipeline/ProviderInvocationPipeline`，由 `ProviderInvocationStage.order()` 升序决定，外层 order 小）：

```
Bulkhead(providerKey, max_concurrency)            order=100
  └─ CircuitBreaker(providerKey)                  order=200
       └─ RateLimiter(providerKey, effectiveRate) order=300
            └─ Retry(retryPolicy, 含整链墙钟预算)   order=400
                 └─ Timeout(timeout_ms, 单次尝试)   order=500
                      └─ provider.fetchComments(request)
```

顺序理由：先隔离并发（防线程耗尽）→ 再快速失败（熔断）→ 再控速 → 再重复尝试（重试成本最高，放最内层的**外层**）→ 每次尝试各自限时。

**与原计划的差异（重要，勿按旧图理解）**：本节原先画的是 `Timeout` 在 `Retry` **之外**（= 整条重试链只有一个时限）。实施时改为 `Retry` 在外、`Timeout` 在内，理由是 §9.5 明确 `providers[].timeout_ms` 是**单次调用超时**，并给出 `子任务整体 = 单次调用超时 × (max_retry+1) + 退避总和` —— 该公式只在"每次尝试各自限时"时成立。

两个方向都保住的具体做法：
1. `TimeoutStage` 用 `future.get(timeoutMs)` 限**单次尝试**（超时抛 `ProviderTimeoutException.singleCall`）;
2. `RetryStage` 另算一条**整链墙钟预算** `timeoutMs × (maxRetry+1) + 500 × (2^maxRetry − 1)`（`InvocationContext.totalBudgetMs()`），退避会超预算或尝试后已过预算就抛 `ProviderTimeoutException.totalBudget`。

这样"单次调用有独立超时"与"整条链不会无限拖长"同时成立。`maxRetry = 0` 时不报总预算耗尽（没有重试链，单次超时异常本身就是最准确的描述）。

三条边界的实测数值（E2E 配置 `timeout_ms=3000`、`max_retry=1`、退避基值 200ms）：`totalBudgetMs() = 3000×2 + 200 = 6200ms`，实测请求耗时 **6315ms**，返回 `单次调用超时（> 3000ms）` 而非"总预算耗尽" —— 两条防线都在，且报的是更准确的那条。

### 8.2 自适应限速 `[借鉴 B-11]` `[已实现]`

实现：`core/ratelimit/` —— `AdaptiveDelayPolicy`（纯计算）+ `AdaptiveRateLimiter`（状态与联动）+ `FlowEffect`。

```
参数（每个 providerKey 独立，全部可选，缺省走代码默认值）：
  static_rate        = platform_feature_config.providers[].rate_per_second     ← 有效速率的**上限**
  target_concurrency = providers[].target_concurrency（默认 1.0）
  start_delay_ms     = providers[].start_delay_ms（默认 500）    ← 延迟**下限**
  max_delay_ms       = providers[].max_delay_ms（默认 60000）    ← 延迟**上限**

每次调用返回后：
  target_delay = latency_ms / target_concurrency
  new_delay    = (old_delay + target_delay) / 2
  if 本次为失败/非成功状态：new_delay 只允许增大，不允许减小
  new_delay = clamp(new_delay, start_delay_ms, max_delay_ms)
  effective_rate = min(static_rate, 1000 / new_delay)
```

> 目的：**错误率升高时自动降速**，避免"失败越猛打越猛"放大故障。

**三层职责划分**（刻意分开，便于各自验证）：

| 组件 | 职责 |
|---|---|
| `AdaptiveDelayPolicy` | **纯计算**：由本次耗时推导下一次延迟；无状态、可脱离 Spring 直接断言 |
| `AdaptiveRateLimiter` | 持有每供应商的延迟与预热起点，算有效速率、驱动令牌桶、按节流写库 |
| `ProviderRateLimitManager` | 令牌桶本身（Guava `RateLimiter`），新增静默热更新 `syncRateQuietly` |

**与熔断器的分工**：熔断器管"**要不要打**"（三态开关，质变）；自适应限速管"**打多快**"（连续调参，量变）。
两者的结果上报**收敛到唯一入口** `DynamicProviderRouter.markProviderOutcome(...)` ——
这是 C-12 的教训：同一份事实若由两条路径分别写入，漏报一处就会让两个视图永久分裂。

**落库**：`effective_qps` / `adaptive_delay_ms` 写回 `supplier_state`，用 `SupplierStateDao#updateAdaptiveMetrics`
的 `$set` 定点更新，**与熔断器的整档写入互不覆盖**（`$set` 只碰这两个字段）。

> ⚠️ 若用 `save()` 整档替换，两个写者会互相清空对方的数据 —— 但若只写 `$set`，又必须保证字段**已声明在实体上**，
> 否则 `MongoTemplate` 会把字段名原样写入（驼峰），见 §5.0.2。

### 8.3 流控效果 `[借鉴 B-14]` `[已实现]`

| `FlowEffect` | 行为 | 取令牌等待 |
|---|---|---|
| `REJECT`（默认） | `tryAcquire` 失败即跳过该供应商，压力转移给下一个候选 | `collector.ratelimit.reject-timeout-ms`（默认 500ms） |
| `WARM_UP` | 冷启动/熔断恢复后按预热曲线从低速率平滑升到 `effective_rate`；拒绝语义同 `REJECT` | 同上 |
| `THROTTLE_QUEUE` | 匀速排队（漏桶），等到令牌才走，超时才拒绝 | 供应商的 `max_queue_wait_ms`，缺省用 `collector.ratelimit.max-queue-wait-ms`（默认 2000ms） |

**配置位置**：`platform_feature_config.providers[].flow_effect`（字符串，大小写不敏感；未知值回退 `REJECT`，
避免配置写错就让采集链路失败）。

**预热与熔断恢复的联动**：`AdaptiveRateLimiter` 监听 `CircuitStateChangedEvent`，
供应商从 `OPEN` 恢复（`→ CLOSED`）时重新开始预热，避免"刚恢复就以满速打回去"导致立刻二次熔断。
这是 `[B-21]` 状态迁移事件的**第一处实际消费方** —— 说明"状态迁移发事件"这个设计确实能解耦出后续能力。

### 8.4 重试策略 `[借鉴 B-04][B-07]`

| 策略 | 退避公式 |
|---|---|
| `FIXED` | `base_ms` |
| `EXPONENTIAL`（默认） | `min(base_ms × 2^(n-1), retry_max_ms) + random(0, jitter_ms)` |

- 重试**不阻塞线程**：置 `RETRYING` + `next_execute_time`，由调度器重新拾取（修正 C-33 的 `Thread.sleep`）。
- 位移溢出封顶（修正 C-33）。
- 区分**可重试异常**（网络/超时/5xx）与**不可重试异常**（参数错误/URL 不支持）：后者直接失败，不重试。

### 8.5 熔断器 `[已实现]`

实现：`core/circuit/` —— `CircuitState` / `CircuitBreakerConfig` / `ProviderCircuitBreaker` / `CircuitStateChangedEvent`。

```java
record CircuitBreakerConfig(
    double failureRateThreshold,   // 失败率阈值（%）
    long   slowCallMs,             // 慢调用判定，<=0 关闭慢调用统计
    double slowCallRateThreshold,  // 慢调用比例阈值（%）
    int    slidingWindowSize,      // 滑动窗口请求数
    int    minimumCalls,           // 触发统计的最小请求数
    long   openSeconds,            // 熔断时长
    int    halfOpenCalls           // 半开放行探测数
) {}
```

- 状态机见 §5.6；状态迁移发布 Spring 事件 `ApplicationEventPublisher` `[借鉴 B-21]`。
- **`supplier_state.circuit_state` 是唯一健康真相源**（修正 C-12）：
  - `providers[].is_healthy` 降级为**运维强制下线开关**，程序只读不写，与熔断状态**取与**；
  - 写：`ProviderCircuitBreaker` 即时写穿到 `supplier_state`（状态迁移一定立即落库，纯计数按 `persist-interval-seconds` 节流）；
  - 读：路由 `select()` 第 4 步查熔断状态，不再读 `health_status`。
- 恢复路径：`HALF_OPEN` 放行 `halfOpenCalls` 个探测，全成功 → `CLOSED`；任一失败 → `OPEN`。
- **成功也必须上报**：原实现只写失败不写成功，供应商一旦 DOWN 就永远 DOWN —— 这是 C-12 的另一半。
- 重启不丢状态：`ProviderCircuitBreaker` 惰性从 `supplier_state` 恢复，OPEN 的供应商不会因重启立刻被重新打。
- `health_status`（UP/DOWN/DEGRADED）保留为 `circuit_state` 的人读投影，**不参与路由判定**。
- `reset(platform, feature, providerKey)` 供运维在上游确认修复后立即恢复流量（自动恢复路径才是常态）。
- `enabled=false` 时全部放行且不统计（用于排障时快速隔离熔断逻辑本身）。

**两个实现细节（都是验证阶段实测发现的坑）**

1. **慢调用阈值必须在成功路径也评估**。慢调用通常仍然"成功"，若只在失败路径评估，`slowCallRateThreshold` 永远不会生效。
2. **半开探测名额必须可回收**。名额在路由阶段领走，但候选可能因限流或"前一个候选已成功"而根本没被执行；
   若不回收，`halfOpenPermits` 会一直是 0，熔断器**永久卡在 HALF_OPEN 拒绝一切请求**。
   兜底：进入 HALF_OPEN 后超过 `openSeconds` 仍未集齐探测结果 → 重新发放名额并告警。

**相关配置**（`application.properties`）

| 配置项 | 默认 | 含义 |
|---|---|---|
| `collector.circuit.enabled` | true | 总开关 |
| `collector.circuit.failure-rate-threshold` | 50 | 失败率阈值 % |
| `collector.circuit.slow-call-ms` | 10000 | 慢调用判定；≤0 关闭慢调用统计 |
| `collector.circuit.slow-call-rate-threshold` | 80 | 慢调用比例阈值 % |
| `collector.circuit.sliding-window-size` | 20 | 滑动窗口请求数 |
| `collector.circuit.minimum-calls` | 5 | 最小调用数（冷启动防误判） |
| `collector.circuit.open-seconds` | 60 | 熔断时长 |
| `collector.circuit.half-open-calls` | 3 | 半开探测数 |
| `collector.circuit.persist-interval-seconds` | 30 | 纯计数落库节流（状态迁移不受此限） |

> 非法配置会被 `CircuitBreakerConfig.sanitized()` 收敛到安全范围
> （`openSeconds` 下限 1 秒等），避免配错一次就把所有供应商永久熔断。

> 另已验证：重跑 `db/init-comment-collector.js` **不会**抹掉在线熔断状态

**与调用管线的交界（C-44，2026-09-24 实测）**：熔断器只应统计**真正触达供应商**的调用。若把管线自身的保护性拒绝（Bulkhead 满 / 限流未取到令牌 / 熔断闸门拒绝）也计成失败，就会**因果倒置** —— 并发压力越大、拒绝越多、失败率越高，最后把完全健康的供应商熔断掉。

### 8.6 过载保护 `[借鉴 B-16]` `[已实现]`

| 层 | 手段 | 状态 |
|---|---|---|
| 入口 | 队列名额不足 → 新的 ASYNC 提交返回 `503 Service Busy` | **✅ 已实现**（修正 C-19） |
| 调度 | 批次大小自适应：积压越多，批次越大（上限 `batch-size-max`） | 未实现（公平配额已是固定轮次，见 §7.6.3） |
| 供应商 | Bulkhead + 熔断 + 自适应降速 | 熔断 ✅（§8.5）；Bulkhead/自适应降速见 P2-7/P2-8 |

**实现要点（`PriorityTaskQueue` 的容量语义）**

```
tryReserve(n)     原子预留 n 个名额；不足则**一个都不预留**并返回 false
offerReserved(t)  用已预留的名额入队
release(n)        归还未使用的预留名额
offer(t)          = tryReserve(1) + offerReserved(t)   ← 便捷形式，本身也是原子的
removeBest(...)   每移除一个元素归还 1 个名额
```

**为什么必须是"原子预留"而不是"先查容量再入队"** `[已实测]`

第一版实现是 `if (remainingCapacity() < needed) throw ...` 再逐个入队。10 个并发请求（`queue-capacity=2`）的实测结果是
**10 个全部返回 200**：所有请求都在同一毫秒内通过检查，谁都没看到别人占用的名额（典型 TOCTOU）。
加入 `tryReserve` 后同样场景变为 **2 个 200 + 8 个 503**。

单元侧也钉住了这一点：`capacity=10`、20 个线程各"预留 1 个并立即入队"，**恰好 10 个成功**（§8.6.1 用例 [15]）。

**为什么要求"整批预留"**：`createMasterTask` 按 `links.size()` 一次性预留。
否则一个 10 链接的请求会出现"前 2 个链接受理、后 8 个拒绝"的**部分受理** —— 调用方既拿不到 503、也无法整批重试。
未被用掉的名额在 `finally` 中归还。

**拒绝的位置**：预留发生在**任何记录落库之前**，因此被拒绝的请求不会留下
"主任务已建、子任务拆了一半"的脏数据（实测：10 并发只产生 2 条 `master_task`）。

**兜底路径**：恢复扫描等"不属于已预留批次"的提交走 `collectAsync`（自行预留 1 个）；
若原子预留失败，则该子任务被置为 `FAILED` 并收敛主任务状态，而**不是**抛异常中断循环
—— 否则子任务会永远停在 `RUNNING`、主任务永远不完成。

#### 8.6.1 验证方式 `[已实测]`

`PriorityTaskQueue` 是纯组件，可脱离 Spring 直接验证。2026-09-23 实测 **53/53 通过**，其中与过载保护直接相关的：

| # | 场景 | 期望 |
|---|---|---|
| 2 | `capacity=3` 连续入队 | 前 3 个成功，第 4 个返回 false，长度不变 |
| 3 | 满队列 `poll()` 后再入队 | 成功（**容量许可必须归还**，否则队列"只出不进"） |
| 4 | `pollIf` 未匹配到元素 | 不归还名额（否则容量被超发） |
| 10 | 20 轮"填满→取空" | 许可无泄漏、无超发 |
| 12 | `tryReserve(3)` 在只剩 2 时 | 返回 false 且**剩余仍是 2**（无部分预留） |
| 15 | 20 线程抢 10 个名额 | **恰好 10 个成功**（旧的"先查后入队"此处会 20 个全过） |

### 9.2 调用管线 `[借鉴 B-12]` `[已实现]`

包：`core/pipeline/`。管线是**供应商调用的唯一边界** —— 门面只说"调用哪个供应商"，限流/熔断闸门/并发隔离/重试/限时/成败判定/结果上报全部由管线承担。

```java
public interface ProviderInvocationStage {
    int order();                     // 小的在外层
    String name();
    <T> T invoke(InvocationContext ctx, Supplier<T> next);
}
// 阶段常量（ProviderInvocationStage.Stages）：
// BULKHEAD=100, CIRCUIT_BREAKER=200, RATE_LIMIT=300, RETRY=400, TIMEOUT=500
```

`InvocationContext` 是一个不可变 `record`，一次调用链的共享上下文：

```java
public record InvocationContext(CommentCollectRequest request, String platformCode, String featureCode,
                                ProviderConfig provider, long timeoutMs, int maxConcurrency, int maxRetry) {
    String providerKey();      // weibo_official
    String supplierKey();      // weibo:comment:weibo_official
    long totalBudgetMs();      // timeoutMs*(maxRetry+1) + 500*(2^maxRetry - 1)，用于整链墙钟预算
}
```

已实现阶段：

| 阶段 | 职责 | 拒绝/失败时抛出的异常 |
|---|---|---|
| `BulkheadStage` | 按 `supplierKey` 限并发（`Semaphore(maxConcurrency, true)`） | `BulkheadFullException`（**不排队，立即失败**） |
| `CircuitBreakerStage` | 执行前**权威闸门**（委托 `router.allowProvider`） | `ProviderInvocationException`（处于熔断状态） |
| `RateLimitStage` | 领令牌（委托 `router.tryAcquireProvider`） | `RateLimitedException`（含 `effect` 与有效速率） |
| `RetryStage` | 重试 + 退避 + **整链墙钟预算** | `ProviderTimeoutException.totalBudget` / 包装后的最后一次失败 |
| `TimeoutStage` | **单次尝试**限时；有上限线程池，不排队 | `ProviderTimeoutException.singleCall` |

装配与开关：

- 总开关 `collector.pipeline.enabled=false` → 所有阶段直连 `provider.fetchComments(request)`（压测逐项隔离用）。
- 单阶段开关：`collector.pipeline.bulkhead-enabled` / `collector.pipeline.timeout-enabled`。
- 启动日志直接给出装配结果：`供应商调用管线已装配: Bulkhead → CircuitBreaker → RateLimit → Retry → Timeout → provider.fetchComments | enabled=true timeout=3000ms 默认并发上限=4`。

五个实施要点（都是实测后定的，不是照搬文档）：

1. **成败判定在重试环之内**。`validate`（null 判定 + `status != STATUS_SUCCESS` 判定，消息与 §9.4 逐字一致）在 `TimeoutStage` 之后、每次尝试内执行；放在环外会让"用 `status` 表达失败"的供应商**一次都不被重试** —— 本项目 9 个供应商全部属于这一类，`max_retry` 曾因此形同虚设。
2. **只有真正触达供应商的调用才上报运行时状态**。`invoke` 用跨线程可见的 `AtomicBoolean attempted` 标记"是否真的执行到了 `fetchComments`"（供应商代码可能跑在限时线程池的线程上），`finally` 里 `if (attempted.get())` 才调 `router.markProviderOutcome(...)`。
   - 否则 Bulkhead/限流/熔断闸门自身的保护性拒绝会被计成供应商失败 → **并发压力越大、失败率越高，最后把完全健康的供应商熔断掉**（因果倒置，见 C-44 与 §8.5.1 的定量证据）。
3. **Bulkhead 拒绝不排队**：排队只是把"下游慢"换成"队列长"，被占住的线程一样消耗；立即失败后由门面切换下一个候选。
4. **`TimeoutStage` 用 `SynchronousQueue` + 有上限线程池**：排队会让"限时"承诺失效（排队时间也计入调用方等待）；池满时立即抛异常（消息含"限时线程池已满"）。
   - 已知边界：`future.cancel(true)` **不能终止底层 OkHttp 请求**（OkHttp 的 `callTimeout` 默认 60s 才是网络层的真正截止线）。因此"超时"保证的是**调用方按时返回**，不保证上游请求已停；在途请求总量仍由 Bulkhead 兜住（信号量覆盖整条链）。
   - 副作用：供应商代码在 `collector-provider-*` 线程执行，不再是消费者线程（本项目无 ThreadLocal 依赖，无影响）。
5. **`timeout_ms = 0` / `max_concurrency = 0` 视为"不限"**，而不是回退全局默认；缺省（null）才回退 `${collector.pipeline.timeout-ms}` / `${collector.pipeline.default-max-concurrency}`。

**门面不再承担的职责**：`CommentCollectionFacade` 删除了自己的限流调用与重试调用，`RetryableProviderExecutor` 已删除（避免两条重试路径）。门面只保留"选谁"（路由）、"切换下一个候选"、落库与结果组装。

**失败语义（有意区分，两条路径不同）**：

| 路径 | 供应商失败时的返回 | 理由 |
|---|---|---|
| 候选列表路径（未指定供应商） | `200` + `success=false` + `errorMessage=所有供应商均不可用: {key=原因, …}` | 中间件已尽力在候选间切换，属于"业务上没采到"，调用方可读 `errorMessage` 决定后续 |
| 指定供应商路径（`specifiedProviderKey`） | **`503`** + `code=PROVIDER_UNAVAILABLE` + `{providerKey, reason}` | 调用方点名了供应商，就该知道"是它现在不行、可稍后重试"，而不是拿到无法区分的 `200 + success=false` |

⇒ 503 是**本服务唯一应当重试的错误码**（另一条是 §8.6 的过载 503 `SERVICE_BUSY`）。

### 9.4 评论落库 `[已实现]` `[借鉴 B-23][B-29]`

**统一成败判定已上移到管线**（§9.2 要点 1）：`ProviderInvocationPipeline#validate` 负责 null 与 `status != STATUS_SUCCESS` 判定，并在**重试环内**执行，因此失败状态会先触发重试、重试耗尽才抛异常。消息与下表逐字一致：

```java
// ProviderInvocationPipeline#validate（管线内，重试环内）
if (entity == null) throw new CollectorException("供应商 [" + providerKey + "] 返回 null");
if (entity.getStatus() != CommonStatusEnum.STATUS_SUCCESS) {
    // 关键：供应商用 status 表达失败时也必须抛异常，否则会被当成"成功但无数据"
    throw new CollectorException("供应商 [" + providerKey + "] 返回失败状态: " + entity.getStatus()
            + (entity.getMsg() == null ? "" : " / " + entity.getMsg()));
}
```

**落库仍留在门面**（`CommentCollectionFacade#toResult` → `#persist`，只在 `request.taskId` 非空时落库）：管线的边界是"供应商调用"，落库属于本服务的业务动作，不放进管线。

```java
// CommentCollectionFacade#toResult（管线返回后的成功路径）
List<Comment> comments = entity.getDataList() == null ? Collections.emptyList() : entity.getDataList();
persist(request, providerKey, comments);          // ← 落库
return CommentCollectResult.builder()
        .success(true).providerUsed(providerKey).comments(comments)
        .hasMore(Boolean.TRUE.equals(entity.getHaseMore()))
        .nextCursor(entity.getNextUrl())          // ← 翻页游标透出给调用方
        .build();
```

- 落库走 `CommentDao`（`domain/dao/CommentDao.java`），实体为 `CommentDoc`（集合 `comment`）。
- **业务主键去重**：`_id = taskId-mid-commentId`（见 §5.5），重复采集同一条评论是覆盖而非新增；
  `CommentDao.saveAll` 先 `insertAll`、失败退化为逐条 `save`，与 `auto-task-web` 写法一致。
- **不落库的场景**：`request.taskId` 为空（纯同步即时返回）时跳落库，只走内存返回。
- **落库失败不影响返回**：`persist` 内部 catch 全部异常并只记日志，采集结果仍会正常返回给调用方。
- `[借鉴 B-13]` 与 Scrapy 的去重过滤器同构：靠业务主键保证幂等，而不是先查后写。

### 9.5 超时控制 `[借鉴 B-03]` `[已实现]`

| 层 | 超时 | 实现与默认值 |
|---|---|---|

|---|---|---|
| `connectTimeout` / `readTimeout` / `writeTimeout` | 30s / 30s / 30s | `HttpUtil.Builder` 默认 |
| `callTimeout` | **60s** | 覆盖 DNS/建连/写/读的整次调用，**才是网络层真正的兜底截止线** |
| `maxRetry` | **3** | `HttpUtil` **自带**的重试策略，与管线 `RetryStage` 的 provider 层重试**叠加**（最坏情况尝试次数相乘） |
| 连接池 | `ConnectionPool(200, 3min)` | |

⇒ 两条硬约束：`collector.pipeline.timeout-ms` **不应大于 OkHttp 的 `callTimeout`（60s）**，否则超时保证失效（管线已放弃等待但请求还在跑）；供应商 `max_retry` 与 HttpUtil 的 3 次内部重试是叠乘关系，`max_retry` 配大时会显著放大上游压力。

实测验证（`timeout_ms=3000`、`max_retry=1`、退避基值 200ms）：`totalBudgetMs()=6200ms`，实测请求耗时 **6315ms** 后返回 `单次调用超时（> 3000ms）`。

### 9.6 优雅停机 `[借鉴 B-08]`

```java
@Component
class CollectorLifecycle implements SmartLifecycle {
    stop() {
        accepting = false;                 // 停止接收新任务
        dispatchPool.shutdown();           // 不再派发
        providerPool.shutdown();
        providerPool.awaitTermination(gracePeriod);   // 等待在途完成
        providerPool.shutdownNow();        // 超时强制
        flushRunningSubTasks();            // RUNNING → PENDING（供下次启动恢复）
    }
}
```

## 10. 供应商接入规范

### 10.1 接口契约

```java
public interface CommentProvider {

    /** 供应商唯一标识，必须与 Spring Bean 名称一致。 */
    String providerKey();

    /**
     * 执行评论采集。
     * <p>失败时<b>必须</b>满足下列之一，否则框架无法识别失败：
     * <ul>
     *   <li>抛出异常（网络异常、解析异常）；</li>
     *   <li>返回 {@code CommonEntity.status != STATUS_SUCCESS}。</li>
     * </ul>
     */
    CommonEntity<Comment> fetchComments(CommentCollectRequest request);
}
```

> **这条契约是修正 C-06 的核心**：当前 4 个真实 Provider 在失败时返回 `STATUS_ERROR` 而不抛异常，
> 而 Facade 只捕获异常 → 不重试、不切换、还返回 `success=true`。

### 10.2 实现约定

1. **Bean 名 = `providerKey`**：`@Component("weibo_official")`；`[借鉴 B-30]` 另加 `@ProviderCapability` 声明能力，启动时校验与 DB 一致。
2. **HTTP 一律走 `HttpUtil`**：由 `HttpClientConfig` 提供单例 Bean，**禁止**各 Provider `new HttpUtil.Builder().build()`
   （当前 4 份独立连接池，C-37）。
3. **不得硬编码地址与凭据**：全部来自配置（参考 `auto-task-web` 的 `GolaxyConstants.getCommentBaseUrl()` 做法，C-25）。
4. **`extra` 允许为 null**：取值前必须判空（C-21）。
5. **分页约定**：
   - Golaxy 系（B站 / 小红书）：游标 `cursor`，**首页不传该参数**；
   - 抖音 / 头条：页码 `page`，从 1 开始；
   - 单次 HTTP 失败**内部重试 3 次、间隔 1s**（与框架层的"供应商切换级重试"职责不同）。
6. **子评论**：`extra.commentId` 非空时走子评论接口，并设置 `parent_comment_id`。

- 关键状态迁移（子任务终态、熔断状态变化、供应商切换）单独打 `WARN`/`INFO`，便于审计（`[借鉴 B-10]`）。

**调用管线与容错链的关键日志关键字**（排障时直接 grep）：

| 关键字 | 含义 |
|---|---|
| `供应商调用管线已装配` | 启动期打印装配顺序与生效超时/默认并发 |
| `Bulkhead 额度初始化: key=… maxConcurrency=…` | 该供应商的并发上限（来自 `providers[].max_concurrency`） |
| `初始化限流器: key=… rate=…/s` | 该供应商的静态速率上限 |
| `重试 n/m: provider=… 等待…ms` | 退避时长（`retry-backoff-base-ms × 2^(n-1)`） |
| `熔断闸门拒绝: key=… state=OPEN` | 执行前闸门拦截，**未发起调用** |
| `熔断器 OPEN/HALF_OPEN/CLOSED: key=… ← … 原因=…` | 状态迁移（含失败率/慢调用率与冷却秒数） |
| `供应商执行失败，切换: provider=…` | 候选列表路径下切换到下一个候选 |
| `未触达供应商，跳过运行时状态上报`（DEBUG） | 保护性拒绝未计入熔断统计（C-44 的正常行为） |
| `限流拒绝: key=… rate=…/s` | 未取到令牌（`[借鉴 B-14]` 的 `REJECT` 语义） |
| `供应商不可用: provider=… type=… message=…` | 指定供应商路径以 503 返回（`GlobalExceptionHandler`） |

### 15.3 关键场景用例

| 场景 | 步骤 | 期望 |
|---|---|---|
| 供应商慢 → 自适应降速 | Fake 延迟递增 | `effective_qps` 单调下降并稳定在 `1000/latency` 附近 |
| 供应商返回 `STATUS_ERROR` | Fake 返回 `STATUS_ERROR` | 视为失败 → **重试（`max_retry` 次）** → 切换（验证 C-06 修复；`validate` 在重试环内，否则 9 个"用 status 表达失败"的供应商一次都不会被重试） |
| 熔断期间请求 | 熔断后继续提交 | 快速失败，不占用 providerPool 线程 |
| 队列溢出 | 灌入超过 `queue-capacity` | 返回 503 服务繁忙，不 OOM |
| 并发超 Bulkhead 上限 | 3 并发打 `max_concurrency=1` 的供应商 | 1 个真实执行，其余**立即** 503（不排队） |
| 保护性拒绝不污染熔断 | 先制造 Bulkhead/限流拒绝，再制造真实失败 | 熔断窗口只统计真实失败（C-44） |
| 优雅停机 | 在途 10 个任务时 `SIGTERM` | 等待完成，`RUNNING` 未完成的回置 `PENDING` |
