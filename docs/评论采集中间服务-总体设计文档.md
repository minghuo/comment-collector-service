## 1. 项目概述

### 1.1 目标

构建一个**多平台、多供应商的评论采集中间服务**，屏蔽底层数据供应商（官方 API、第三方服务、自研爬虫）在成本、速率、稳定性上的差异，
对外提供统一的任务提交、调度、执行与结果返回能力。

### 1.2 范围

**本期包含**
- 多平台评论采集：`weibo`、`douyin`、`xhs`（小红书）、`bilibili`、`toutiao`
- 主任务/子任务两级模型；同步即时返回 + 异步任务两种模式
- 供应商路由、限流、重试与故障切换
- 优先调度与防饥饿
- 任务持久化与重启恢复

**本期不含（列入 §17 后续阶段）**
- 微信平台、互动指标更新、账号历史
- 管理后台 UI、接口鉴权、集群化部署
- 具体爬虫的反爬对抗（由各供应商实现类自行承担）

### 1.3 术语

| 术语 | 说明 |
|---|---|
| 平台 | `platformCode` ∈ {`weibo`, `douyin`, `xhs`, `bilibili`, `toutiao`} |
| 功能 | `featureCode`，本期仅 `comment` |
| 供应商 | 实现某平台某功能的数据提供方，由 `providerKey` 标识，**必须与 Spring Bean 名一致** |
| 主任务 | 一次完整采集请求，关联一个或多个链接 |
| 子任务 | 主任务按链接拆分的执行单元，是**调度的最小单位** |
| 即时返回（SYNC） | 同步等待执行完成并返回结果，不产生任务记录 |
| 任务模式（ASYNC） | 返回任务 ID，异步执行，调用方轮询 |
| 有效优先级 | `priority - agingCount × boost`，**数值越小越优先** |
| 熔断 | 供应商连续失败后暂时隔离，冷却后半开放行探测 |

**统一约定**

1. **一页一次调用**：`CommentProvider#fetchComments` 每次只取一页；翻页靠返回的
   `CommonEntity.haseMore` + `nextUrl`（游标/页码），调用方回填到 `request.extra` 后再次调用。
2. **入参**：`request.extra` 承载供应商参数（`cookie` / `mid` / `cursor` / `page` / `buffer` / `commentId` …），
   由 `TaskManagementService#parseExtra` 从任务的 `requestParams`(JSON) 解析而来。
3. **内容 ID 解析**：`ProviderUrls.resolveMid`（通用取链接最后一段）与 `WeiboUrlParser`
   （`WeiboTool.urlToMid` + uid 正则）负责从链接推导 `mid`，无需调用方额外传参。
4. **失败表达**：抛异常或返回 `status != STATUS_SUCCESS` 都算失败，二者都会被框架识别（见 §9.2）。
5. **内部重试**：每个供应商对单次 HTTP 调用内部重试 3 次（间隔 1s），
   与框架层的"供应商切换级重试"职责区分。

> ⚠️ **上游业务码必须校验**：中科天玑接口在业务失败时会返回 HTTP 200 +
> `{"code":500,"message":"获取评论信息失败, 请重试", ...}`。仅判断 `body.contains("comments")`
> 会把这种响应误判成"成功但无数据"，导致既不重试也不切换供应商。四个 Golaxy 供应商均已加 `code != 200 → 失败` 判断。

## 5. 数据模型

### 5.0 数据访问与命名约定（重要）

#### 5.0.1 数据访问：`MongoTemplate` + `auto-task-web` 的 DAO 风格 `[已实现]`

**决策：所有 MongoDB 访问统一走 `MongoTemplate`，写法对齐 `auto-task-web` 的 `dao` 包，不使用 Spring Data 的 `MongoRepository`。**

| 项 | 说明 |
|---|---|
| 数据源 | 单一数据源，由 Spring Boot 自动配置（`spring.data.mongodb.uri`）；**不再自定义多数据源**（原 C-10 已消除） |
| 包 | `com.sysj.collector.dao`（对应 `auto-task-web` 的 `com.sysj.auto.task.web.dao`） |
| 类 | `MasterTaskDao` / `SubTaskDao` / `PlatformFeatureConfigDao` / `UserTierConfigDao` / `SupplierStateDao` |
| 注解与注入 | `@Component` + `@Slf4j`；`@Resource private MongoTemplate mongoTemplate;`（与 auto-task-web 一致） |
| 方法风格 | 每个 DAO 自包含，`Query`/`Criteria`/`Update` **内联在方法体内**，不抽公共基类、不抽字段常量类 |
| 批量写入 | `saveAll` 先 `insertAll`，失败后逐条 `save` 兜底（照搬 auto-task-web 的写法） |
| 数据归属 | 数组元素的 `$` 位置更新（供应商健康/速率）下沉到 `PlatformFeatureConfigDao`，Service 层不持有 `MongoTemplate` |
| `_class` 字段 | 已通过 `MongoConfig` 关闭（`DefaultMongoTypeMapper(null)`），文档中不写入 `_class` |

**为什么不用 `MongoRepository`**

1. 派生查询无法承载后续调度所需的**原子抢占**（`findAndModify`）、`$` 数组元素更新、字段投影、批量 upsert；
2. Repository 与手写 `MongoTemplate` 若指向不同数据源，会出现"写到另一个库"的事故（原 C-10）；
3. 与 `auto-task-web` 保持同一种数据访问写法，跨项目阅读成本最低。

> 注：`auto-task-web` 的 DAO 里带 `stream`（流式导出）、`skip/limit`（分页）、`cleanOldData`（过期清理）等能力，
> 本项目的 `SubTaskDao` 也保留了 `streamByMasterTaskId` / `getSubTasksByMasterTaskId`（分页）供后续导出与查询接口使用。

#### 5.0.2 字段命名：落库下划线式，但**查询可用驼峰** `[已实现，实测]`

`application.properties` 配置了：

```properties
spring.data.mongodb.field-naming-strategy=org.springframework.data.mapping.model.SnakeCaseFieldNamingStrategy
```

因此**落库字段名是下划线式**（实测原始文档）：

```
platform_feature_config : platform_code / feature_code / feature_name / status / providers[].provider_key / is_healthy
master_task             : user_id / platform_code / total_links / create_time ...
sub_task                : master_task_id / aging_count / retry_count / max_retry ...
```

> ⚠️ **重要更正（2026-09-23 实测）**：此前认为"手写 `Criteria`/`Update` 必须写下划线名，写驼峰会静默匹配 0 条"是**误判**。
> `MongoTemplate` 在执行前会经 `QueryMapper` / `UpdateMapper` 按实体映射规则转换字段名，**驼峰与下划线两种写法都能命中**。
> 实测结果：
>
> | 写法 | 命中 |
> |---|---|
> | `Criteria.where("platformCode")`（驼峰） | 1 ✅ |
> | `Criteria.where("platform_code")`（下划线） | 1 ✅ |
> | `Criteria.where("providers.providerKey")`（驼峰嵌套） | 1 ✅ |
> | `Update.set("providers.$.isHealthy")`（驼峰 + `$`） | matched = 1 ✅ |
>
> 结论：**DAO 中统一写驼峰**（与 `auto-task-web` 一致，也与实体字段名一致，可读性更好）。
>
> **唯一例外**：`@CompoundIndex(def = "...")` 的字符串不经过映射器，必须直接写落库名 ——
> 已在 `PlatformFeatureConfig` 中写为 `{'platform_code': 1, 'feature_code': 1}`。
>
> 另：`updateProviderHealth` / `updateProviderRate` 现按 **`matchedCount`** 判定并返回，
> 未命中时打印 WARN（`modifiedCount` 在"值未变化"时也是 0，会误判）。

### 5.6 状态机（统一，替代三份文档的三套枚举）

**主任务**

```
PENDING ──(开始调度)──> ACTIVE ──(全部子任务终态)──> COMPLETED
   │                       │
   └──(创建即失败)─────────┴──> FAILED
```
`PARTIAL_SUCCESS` 为可选终态（部分成功），本期 `[未实现]`。

**子任务**

```
PENDING ──抢占──> RUNNING ──> SUCCESS
   ▲                 │
   │                 ├──(失败, retry_count<max_retry)──> RETRYING ──> RUNNING
   │                 │
   ├──(切换供应商, 重置 retry_count)──────────────────────┘
   │                 │
   │                 └──(全部供应商耗尽 / 熔断)──> FAILED
   └──(misfire 重排 / 重启恢复)
```

**熔断器**（`[借鉴 B-15]`）

```
CLOSED ──(失败率>阈值 或 慢调用比例>阈值)──> OPEN ──(冷却期结束)──> HALF_OPEN
   ▲                                                                    │
   └────────────(探测成功)─────────────────────────────────────────────┤
                                                                        │
   OPEN <──────────────────(探测失败)───────────────────────────────────┘
```

## 6. 核心流程

### 6.1 任务创建（同步 / 异步）

```
POST /api/collect （SYNC）
 1. 参数校验（Bean Validation + 平台/功能存在性 + 链接格式）      [C-16]
 2. 解析用户等级 → 优先级、供应商偏好
 3. 路由：候选构建 → 能力过滤 → 健康/熔断过滤 → 阈值 → 流控
 4. 执行：ProviderInvocationPipeline
 5. 落库：CommentStore.saveAll（业务主键去重）
 6. 返回 CommentCollectResult
 ※ SYNC 不产生 master_task / sub_task 记录

POST /api/tasks （ASYNC）★重构
 1. 参数校验
 2. 创建 MasterTask(status=PENDING) 落库
 3. 按 links 拆分 SubTask(status=PENDING, next_execute_time=now) 批量落库
    · 幂等：唯一索引 (master_task_id, link)，重复提交捕获 DuplicateKey 后忽略  [B-13]
    · overflow_strategy 处理同 target 并发                              [B-02]
 4. MasterTask.status = ACTIVE
 5. 返回 taskId
 6. 【由 SubTaskScheduler 接管执行】← 当前完全缺失（C-13）
```

### 6.2 子任务调度循环 ★ 核心重构

```
SubTaskScheduler（固定间隔轮询，默认 200ms，可配）
 1. 查询候选：
    find({ status: "PENDING", next_execute_time: { $lte: now } })
      .sort({ effective_priority: 1, next_execute_time: 1 })     // 升序 = 优先级高者先
      .limit(batch_size)
 2. 逐个原子抢占（替代读改写，修正 C-32）：
    findAndModify(
      query : { _id: sid, status: "PENDING" },
      update: { $set: { status:"RUNNING", lock_owner: nodeId,
                        lock_expire_time: now+timeout, start_time: now } })
    → 返回 null 说明已被其他节点抢走，跳过
 3. 提交到 providerPool 执行（与调度线程池隔离）[B-06]
 4. 执行完成 → 原子回写 status/result_ref/comment_count/retry_count/cursor
 5. 子任务终态 → 触发主任务计数收敛（findAndModify $inc）
 6. 主任务全部终态 → status = COMPLETED / FAILED
```

**Aging（防饥饿）在此模型下自然生效**：`effective_priority` 在**查询时**计算并写回（或由定时任务批量刷新），
不再依赖 `PriorityBlockingQueue` 的堆重排 —— 一次性解决 C-08。

### 6.3 失败重试与供应商切换

```
1. 执行 fetchComments
2. 失败判定（★修正 C-06）：抛异常 或 status != STATUS_SUCCESS 均视为失败
3. retry_count++ 且 retry_count <= max_retry
   → status=RETRYING，next_execute_time = now + backoff(n)   [B-04]
   → backoff: FIXED = base
              EXPONENTIAL = min(base × 2^(n-1), retry_max_ms) + jitter
   → 重新入队（不阻塞线程）  [B-07]
4. retry_count > max_retry → attempted_providers += provider_key
   → 熔断器记录失败 [B-15]，status=PENDING，reset retry_count
   → 下次调度自动选下一个供应商
5. 所有候选耗尽 → status=FAILED，记 error_message
```

### 6.4 重启恢复与断点续采

```
ApplicationReadyEvent（异步执行，不阻塞启动）
 1. master_task.status IN (PENDING, ACTIVE) 的主任务
 2. 其下 sub_task.status IN (PENDING, RUNNING, RETRYING)
 3. RUNNING 且 lock_expire_time < now → 视为中断，重置：
      status=PENDING, lock_owner=null, next_execute_time=now
    ★ 不再重置 retry_count（保留退避进度）
 4. NEW：cursor / last_page 保留 → 从断点页继续  [B-24]
 5. 调度器自然接管，无需"重新提交请求"（修正 C-14）
```

## 7. 路由与调度设计

### 7.1 路由职责单一化

**当前问题**：`DynamicProviderRouter.route()` 是死代码，`buildCandidates()` 与 `buildOrderedCandidates()` 逐行重复，
门面走的是"自己过滤 + 自己限流"的第二套逻辑，导致 `activation_threshold` 从未生效（C-17/C-18）。

**目标**：路由只保留**一个**入口，语义完整：

```java
ProviderSelection select(RouteContext ctx);
// RouteContext = (platformCode, featureCode, tierConfig, requiredProviderKey, pendingCount)
// 内部顺序：候选构建 → 能力过滤 → 健康/熔断过滤 → 阈值判断 → 流控 → 返回
```

### 7.2 能力过滤 `[借鉴 B-26]`

```java
enum Capability { COMMENT, SUB_COMMENT, CURSOR_PAGING, PAGE_PAGING, SYNC_SUPPORTED, PROXY, LOGIN_STATE }
```

- 供应商在 `platform_feature_config.providers[].capabilities` 声明。
- 请求携带 `requiredCapabilities`（如"要采二级评论"→ `SUB_COMMENT`）。
- 能力不匹配的供应商被过滤 → **直接解决"`supportsSync()` 不存在导致 FR-18 无法判断"的问题**。
- `[借鉴 B-30]` 实现类用 `@ProviderCapability(...)` 声明能力，启动时与 DB 配置做一致性校验
  → **直接解决 C-24「类名/Bean名/注释三者矛盾却无人发现」**。

### 7.3 路由策略枚举 `[借鉴 B-01]`

| 策略 | 语义 | 适用场景 |
|---|---|---|
| `PRIORITY`（默认） | 按 `priority` 升序取第一个可用 | 常规，成本优先 |
| `WEIGHTED` | 按 `weight` 加权随机 | 多供应商按比例分摊 |
| `ROUND_ROBIN` | 轮询（`supplier_state` 记游标） | 均摊成本 |
| `RANDOM` | 随机 | 简单打散 |
| `LEAST_USED` | 取 `total_success` 最小者 | 均衡使用量 |
| `LEAST_RESPONSE` | 取 `avg_response_time` 最小者 | 速度优先 |
| `FAILOVER` | 显式故障转移（失败即换，不重试原供应商） | 高可用优先 |
| `BUSY_TRANSFER` | 取 `in_flight` / `queue_depth` 最小者 | 避免热点 |
| `CONSISTENT_HASH` | 按 `link` 哈希固定供应商 | **保持登录态/游标连续性，提升缓存命中** |
| `SHARDING_BROADCAST` | 广播到全部供应商（分片参数区分） | 大规模补采 |

### 7.4 阻塞与溢出策略 `[借鉴 B-02]`

| 策略 | 行为 |
|---|---|
| `REJECT`（默认） | 同 `(master_task_id, link)` 已存在未完成子任务 → 拒绝新请求并返回已有 `taskId` |
| `DISCARD_LATER` | 丢弃后到的调度（保留先到的执行） |
| `COVER_EARLIER` | 覆盖：取消先到任务，执行后到的 |

- 幂等键 `(master_task_id, link)` 唯一索引是前提（`[借鉴 B-13]`）。

### 7.5 调度过期策略 `[借鉴 B-05]`

| 策略 | 行为 |
|---|---|
| `FIRE_ONCE`（默认） | 若 `next_execute_time` 已过期超过 `misfire_threshold`，立即执行一次（不补跑多次） |
| `IGNORE` | 忽略过期，仅在下一个正常调度点执行 |

### 7.6 优先级与防饥饿

```
effective_priority = max(0, priority - aging_count × aging_priority_boost)

aging 刷新（定时任务，默认 60s）：
  对 status=PENDING 且 wait > aging_interval 的子任务：
    aging_count   = elapsed / aging_interval
    effective_priority = max(0, priority - aging_count × boost)
  超过 max_wait_minutes → effective_priority = 0（最高）

公平配额 [借鉴 B-01 SHARDING_BROADCAST 的配比思想]：
  当高优先级（effective_priority < fair_quota_high_priority_bound）任务占比 ≥ fair_quota_threshold 时，
  每个调度批次保留 ≥ fair_quota_ratio 的名额给低优先级任务。
  ★ 状态必须线程本地或按配额令牌实现，禁止共享 AtomicInteger（修正 C-09）
  ★ 高优先级判定阈值必须来自配置，禁止硬编码 500（修正 C-09）
```

### 7.7 阈值分流

`activation_threshold` 在**统一路由**中生效：待处理数 `< threshold` 时只允许候选列表首位。

## 8. 限流·熔断与降级设计

### 8.1 总体顺序 `[借鉴 B-19]`

```
Bulkhead(providerKey, max_concurrency)
  └─ CircuitBreaker(providerKey)
       └─ RateLimiter(providerKey, effectiveRate)
            └─ Timeout(timeout_ms)
                 └─ Retry(retryPolicy)
                      └─ provider.fetchComments(request)
```

顺序理由：先隔离并发（防线程耗尽）→ 再快速失败（熔断）→ 再控速 → 再限时 → 最后才重试（重试成本最高，放最内层）。

### 8.2 自适应限流 `[借鉴 B-11]`

```
参数（每个 providerKey 独立）：
  static_rate        = platform_feature_config.providers[].rate_per_second
  target_concurrency = providers[].target_concurrency（默认 1.0）
  start_delay_ms     = providers[].start_delay_ms（默认 500）
  max_delay_ms       = providers[].max_delay_ms（默认 60000）

每次调用返回后：
  target_delay = latency_ms / target_concurrency
  new_delay    = (old_delay + target_delay) / 2
  if 本次为失败/非成功状态：new_delay 只允许增大，不允许减小
  new_delay = clamp(new_delay, start_delay_ms, max_delay_ms)
  effective_rate = min(static_rate, 1000 / new_delay)
```

> 目的：**错误率升高时自动降速**，避免当前实现"失败越猛打越猛"放大故障。

### 8.3 流控效果 `[借鉴 B-14]`

| `FlowEffect` | 行为 |
|---|---|
| `REJECT`（默认） | `tryAcquire` 失败即跳过该供应商 |
| `WARM_UP` | 冷启动/熔断恢复后按预热曲线从低速率平滑升到 `effective_rate` |
| `THROTTLE_QUEUE` | 匀速排队（漏桶），超过 `max_queue_wait_ms` 才拒绝 |

### 8.4 重试策略 `[借鉴 B-04][B-07]`

| 策略 | 退避公式 |
|---|---|
| `FIXED` | `base_ms` |
| `EXPONENTIAL`（默认） | `min(base_ms × 2^(n-1), retry_max_ms) + random(0, jitter_ms)` |

- 重试**不阻塞线程**：置 `RETRYING` + `next_execute_time`，由调度器重新拾取（修正 C-33 的 `Thread.sleep`）。
- 位移溢出封顶（修正 C-33）。
- 区分**可重试异常**（网络/超时/5xx）与**不可重试异常**（参数错误/URL 不支持）：后者直接失败，不重试。

### 8.5 熔断器 `[借鉴 B-15]`

```java
record CircuitBreakerConfig(
    double failureRateThreshold,   // 失败率阈值（%）
    long   slowCallMs,             // 慢调用判定
    double slowCallRateThreshold,  // 慢调用比例阈值（%）
    int    slidingWindowSize,      // 滑动窗口请求数
    int    minimumCalls,           // 触发统计的最小请求数
    long   openSeconds,            // 熔断时长
    int    halfOpenCalls           // 半开放行探测数
) {}
```

- 状态机见 §5.6；状态迁移发布 Spring 事件（`[借鉴 B-21]`）。
- **`supplier_state.circuit_state` 是唯一健康真相源**，删除 `platform_feature_config.providers[].is_healthy` 的运行时语义
  （保留为"运维强制下线"开关，二者取与）—— 修正 C-12。
- 恢复：`HALF_OPEN` 放行 `halfOpenCalls` 个探测，全成功 → `CLOSED`；任一失败 → `OPEN`。

### 8.6 过载保护 `[借鉴 B-16]`

| 层 | 手段 |
|---|---|
| 入口 | 队列积压超过 `queue-capacity` → 新的 ASYNC 提交返回 `503 Service Busy`（当前是死配置，C-19） |
| 调度 | 批次大小自适应：积压越多，批次越大（上限 `batch-size-max`） |
| 供应商 | Bulkhead + 熔断 + 自适应降速 |

落库位置：`CommentCollectionFacade#toResult` → `#persist`（只在 `request.taskId` 非空时落库）。

```java
// 供应商返回 → 统一判定成败 → 落库 → 组装返回
private CommentCollectResult toResult(CommentCollectRequest request, String providerKey,
                                      CommonEntity<Comment> entity) {
    if (entity == null) throw new CollectorException("供应商 [" + providerKey + "] 返回 null");
    if (entity.getStatus() != CommonStatusEnum.STATUS_SUCCESS) {
        // 关键：供应商用 status 表达失败时也必须抛异常，否则会被当成"成功但无数据"
        throw new CollectorException("供应商 [" + providerKey + "] 返回失败状态: " + entity.getStatus());
    }
    List<Comment> comments = entity.getDataList() == null ? Collections.emptyList() : entity.getDataList();
    persist(request, providerKey, comments);          // ← 落库
    return CommentCollectResult.builder()
            .success(true).providerUsed(providerKey).comments(comments)
            .hasMore(Boolean.TRUE.equals(entity.getHaseMore()))
            .nextCursor(entity.getNextUrl())          // ← 翻页游标透出给调用方
            .build();
}
```

- 落库走 `CommentDao`（`domain/dao/CommentDao.java`），实体为 `CommentDoc`（集合 `comment`）。
- **业务主键去重**：`_id = taskId-mid-commentId`（见 §5.5），重复采集同一条评论是覆盖而非新增；
  `CommentDao.saveAll` 先 `insertAll`、失败退化为逐条 `save`，与 `auto-task-web` 写法一致。
- **不落库的场景**：`request.taskId` 为空（纯同步即时返回）时跳落库，只走内存返回。
- **落库失败不影响返回**：`persist` 内部 catch 全部异常并只记日志，采集结果仍会正常返回给调用方。
- `[借鉴 B-13]` 与 Scrapy 的去重过滤器同构：靠业务主键保证幂等，而不是先查后写。

**采集结果同时用于两处**

| 用途 | 载体 |
|---|---|
| 即时返回 | `CommentCollectResult.comments`（内存） |
| 异步 / 持续翻页 | `comment` 集合 → `GET /api/tasks/{taskId}/comments`（§11.5） |

## 10. 供应商接入规范

### 10.1 接口契约

```java
public interface CommentProvider {

    /** 供应商唯一标识，必须与 Spring Bean 名称一致。 */
    String providerKey();

    /**
     * 执行评论采集。
     * <p>失败时<b>必须</b>满足下列之一，否则框架无法识别失败：
     * <ul>
     *   <li>抛出异常（网络异常、解析异常）；</li>
     *   <li>返回 {@code CommonEntity.status != STATUS_SUCCESS}。</li>
     * </ul>
     */
    CommonEntity<Comment> fetchComments(CommentCollectRequest request);
}
```

> **这条契约是修正 C-06 的核心**：当前 4 个真实 Provider 在失败时返回 `STATUS_ERROR` 而不抛异常，
> 而 Facade 只捕获异常 → 不重试、不切换、还返回 `success=true`。

### 10.2 实现约定

1. **Bean 名 = `providerKey`**：`@Component("weibo_official")`；`[借鉴 B-30]` 另加 `@ProviderCapability` 声明能力，启动时校验与 DB 一致。
2. **HTTP 一律走 `HttpUtil`**：由 `HttpClientConfig` 提供单例 Bean，**禁止**各 Provider `new HttpUtil.Builder().build()`
   （当前 4 份独立连接池，C-37）。
3. **不得硬编码地址与凭据**：全部来自配置（参考 `auto-task-web` 的 `GolaxyConstants.getCommentBaseUrl()` 做法，C-25）。
4. **`extra` 允许为 null**：取值前必须判空（C-21）。
5. **分页约定**：
   - Golaxy 系（B站 / 小红书）：游标 `cursor`，**首页不传该参数**；
   - 抖音 / 头条：页码 `page`，从 1 开始；
   - 单次 HTTP 失败**内部重试 3 次、间隔 1s**（与框架层的"供应商切换级重试"职责不同）。
6. **子评论**：`extra.commentId` 非空时走子评论接口，并设置 `parent_comment_id`。
