# 评论采集中间服务 · 压测与容量基线方案（阶段2 交付物）

> 版本：v1.0 ｜ 日期：2026-10-05
> 适用对象：运维 / 后端。目标是在阶段 2（Redis Stream 外置队列 + 多实例共享熔断/限速）完成后，
> 用**可重复的压测**建立容量基线，回答三个问题：单实例能扛多少、扩实例能加多少、瓶颈在哪一层。

---

## 1. 被测对象与关键路径

```
POST /api/tasks（整批预检 → Mongo 建任务 → Redis XADD 入队）
    → 消费者线程（XREADGROUP → 幂等守卫(Mongo) → 路由(Mongo缓存) → 管线）
        → Bulkhead(Redis?) → 熔断闸门(Redis Lua) → 限流(Redis Lua 令牌桶)
        → 重试 → 超时 → provider HTTP（外部上游，压测必须 mock）
    → 落库(Mongo bulk upsert) → 结果回写(Mongo 条件更新) → XACK+XDEL
```

**压测原则：上游必须 mock。** 对真实上游压测既不合规也不可重复。
用 `specifiedProviderKey` 指向一个"回显型 mock 供应商"（新增一个测试专用 Provider，
接受请求后睡眠可配置时长并返回固定评论列表），或直接在 dev 环境 hosts 劫持上游域名。

## 2. 场景矩阵

| # | 场景 | 目的 | 变量 | 通过标准（建议基线） |
|---|---|---|---|---|
| S1 | 入口吞吐 | API 层极限 | 并发 50/100/200，每请求 1 链接 | P99 < 100ms，0 错误（队列未满时） |
| S2 | 入口背压 | 503 语义正确性 | 队列灌到 capacity-1 后再打 | 精确 503，XLEN 严格 ≤ capacity，无任务丢失 |
| S3 | 消费吞吐 | 单实例消费极限 | 预灌 10k 消息，mock 供应商 50ms 固定延迟 | 记录 msg/s（基线值），无消息积压增长 |
| S4 | 多实例线性度 | 水平扩展收益 | 1/2/4 实例同跑 S3 | 吞吐 ≈ 线性（≥1.8×/3.4×），熔断/限速状态无分裂 |
| S5 | 限速共享正确性 | 分布式令牌桶 | rate=10/s，2 实例同时打 mock | 聚合 QPS ≈ 10/s（±10%），上游计数 = 单实例配额 |
| S6 | 熔断共享正确性 | Redis 状态机 | 单实例把 mock 打到失败率 60% | 任一实例 OPEN 后**所有**实例的路由过滤剔除该供应商 |
| S7 | 崩溃恢复 | 重启不丢任务 | S3 进行中 kill -9 | 重启后积压继续消费；无子任务永久 RUNNING；主任务计数正确（无翻倍） |
| S8 | 持久化压力 | Mongo 写入 | S3 全速跑 30min | bulk upsert 无报错；主任务状态收敛 O(1)（观察 Mongo 操作数不随任务大小二次增长） |
| S9 | Redis 宕机降级 | 降级兜底正确性 | S3 进行中停掉 Redis 5 分钟再恢复 | ① 停机期间提交返回成功（任务在本地兜底队列）、接口不 500；② 消费者继续消化本地任务；③ 恢复后消费组自动重建、兜底队列回流、XLEN 恢复增长；④ 全程熔断/限流放行兜底无异常风暴；⑤ 降级期间 kill 实例 → 重启后恢复扫描补齐 RUNNING 子任务 |

## 3. 压测执行要点

1. **工具**：Gatling / JMeter / 简单 wrk 脚本均可；S3~S8 的"消息侧"压测直接用
   `redis-cli XADD` 批量灌消息（载荷格式见 `QueuedTask`），绕过 API 层单独测消费端。
2. **观测指标**（压测时必看）：
   - Redis：`XLEN collector:tasks:{high,low}`（积压）、`XPENDING`（在途）、CPU、网络；
   - Mongo：`db.currentOp`、慢查询、`comment` 集合写入速率；
   - 应用：`/actuator/prometheus` 的 `task.*` 指标、JVM 线程数（消费者 = CPU×2 默认）。
3. **容量公式**（单实例消费吞吐的粗估，压测后用实测值替换）：

   ```
   消费吞吐 ≈ min(
       consumerThreads / 平均单任务耗时(s),          ← 线程瓶颈
       Σ min(ratePerSecond_i, 1000/delayMs_i),       ← 供应商限速瓶颈
       Redis Lua QPS 上限,                            ← 一般不是瓶颈（万级/s）
   )
   ```

4. **熔断阈值联调**：S6 顺带验证 `collector.circuit.*` 动态配置（`/api/config` 改完 60s 内生效）。

## 5. 已知边界（压测时留意）

- 重投扫描/断点续采是 DB 扫描型，多实例同时启动会有毫秒级双投窗口（幂等守卫兜底），
  S7 重启场景观察日志中的"重复投递幂等跳过"确认守卫生效；
- mock 供应商**必须**走真实管线（熔断/限流/Bulkhead 全开），否则 S5/S6 无效；
- `collector.queue.claim-min-idle-ms`（默认 10min）必须大于"单任务最长执行时长"，
  S7 前先按 mock 延迟 × (max_retry+1) + 退避核算一遍。
