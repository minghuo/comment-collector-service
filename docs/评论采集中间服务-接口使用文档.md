## 1. 基础信息

| 项 | 值 |
|---|---|
| 协议 | HTTP |
| 默认端口 | `8075` |
| Context Path | `/comment-collector` |
| 基础地址 | `http://{host}:8075/comment-collector` |
| 请求编码 | UTF-8 |
| 请求体格式 | `application/json` |

### 2.3 extra / requestParams 常用参数

同步接口用 `extra`（对象），异步接口用 `requestParams`（**JSON 字符串**，内容等价），键值均为字符串。

| 键 | 适用 | 说明 | 示例值 |
|---|---|---|---|
| `mid` | 微博/B站/抖音/小红书/头条 | 内容 ID；不传时由服务端从链接自动解析 | `5020298753561234` |
| `cookie` | 微博（`local_crawler` / `weibo_repost_local`） | 微博登录 Cookie，**必填**；服务端会从中提取 `XSRF-TOKEN` | `SUB=xxx; SUBP=xxx; XSRF-TOKEN=abc123` |
| `uid` | 微博 `local_crawler` | 微博作者 uid；不传时从链接正则提取 | `1234567890` |
| `sort` | 微博评论 | 排序：`hot`（默认）/ `time` | `time` |
| `replay` | 微博评论 | `1`/`true` 时采二级评论 | `1` |
| `maxId` | 微博评论 | 上一页返回的翻页游标 | `1384212345678` |
| `page` | 抖音/头条/微博转发 | 页码，从 `1` 开始 | `1` |
| `nextId` | 微博转发 | 上一页返回的 `next_cursor` | `1695000000` |
| `cursor` | B站/小红书 | 上一页返回的游标 | `1695000000000` |
| `url` | 公众号 | 文章永久链接（也可直接放 `targetId`） | `https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw` |
| `videoId` | 视频号 | 视频 ID（也可直接放 `targetId`） | `export/UzFfAgtgekIEAQAAAAAA...` |
| `buffer` | 公众号/视频号 | 上一页返回的分页游标 | `eyJvZmZzZXQiOjIwfQ==` |
| `commentId` | 全部 | 父评论 ID；传了则采集该评论的**子评论** | `15023660009290465290` |

> `maxCount` 目前仅作为入参占位，服务端按供应商单页上限（20 条/页）返回，**不按该值截断**。

### 2.4 requiredCapabilities（要求供应商具备的能力）

请求可选带 `requiredCapabilities: ["SUB_COMMENT"]`，要求候选供应商**全部具备**所列能力；
不满足的供应商会被路由直接跳过（不会白失败一次）。

| 能力值 | 含义 | 谁具备（当前） |
|---|---|---|
| `COMMENT` | 能采一级评论 | 全部 15 个 |
| `SUB_COMMENT` | 能采二级评论/回复（`extra.commentId`） | 除 `local_crawler`、`weibo_repost_local`、`honor_bbs_local` 外全部 |
| `CURSOR_PAGING` | 游标翻页（可回传上一页游标继续取） | `weibo_official` / `local_crawler` / `weibo_repost_local` / `bilibili_golaxy` / `xhs_golaxy` / `vivo_bbs_local` / `xiaomi_bbs_local` |
| `PAGE_PAGING` | 页码/偏移翻页 | `weibo_repost_local` / `wechat_sy` / `wechat_video_sy` / `douyin_golaxy` / `toutiao_local` / `tieba_local` / `honor_bbs_local` / `huawei_bbs_local` / `oppo_bbs_local` |
| `SYNC_SUPPORTED` | 支持即时返回（同步接口可直接拿到数据） | 全部 15 个（当前供应商都是同步调用） |
| `PROXY` | 支持走代理（含代理失败自动直连） | `local_crawler` / `weibo_repost_local` / `toutiao_local` |
| `LOGIN_STATE` | 需要登录态/凭据（如微博 Cookie） | `local_crawler` / `weibo_repost_local` |

- **留空 = 不限制**，行为与以前完全一致（老请求无需改动）。
- 无人满足时会明确返回：
  `无候选满足所需能力 [PROXY]；实际候选能力: wechat_sy=[COMMENT, SUB_COMMENT, PAGE_PAGING, SYNC_SUPPORTED]`
  —— 直接告诉你该给哪个供应商补配置、或该换个能力要求。
- 典型用途：要采二级评论就带 `["SUB_COMMENT"]`，避免路由到不支持子评论的供应商后白失败一次。

```bash
curl -X POST 'http://127.0.0.1:8075/comment-collector/api/collect' \
  -H 'Content-Type: application/json' \
  -d '{
    "platformCode": "weibo",
    "featureCode": "comment",
    "targetId": "https://weibo.com/1644948230/NFxYz7abc",
    "requiredCapabilities": ["SUB_COMMENT"],
    "extra": { "mid": "4999020551707430", "commentId": "15023660009290465290" }
  }'
```

#### excludedCapabilities（要求供应商不具备的能力）

与 `requiredCapabilities` 互补的反向约束：候选只要声明了所列能力中的**任意一项**就会被路由剔除。
典型用途是"未提供登录态时不打依赖 cookie 的供应商"——不带 cookie 采微博评论时带
`excludedCapabilities: ["LOGIN_STATE"]`，路由会直接剔除 `local_crawler`、只走 `weibo_official`，
而不是让它先失败一次再靠供应商切换兜底（那会白白污染其熔断统计）。

```bash
curl -X POST 'http://127.0.0.1:8075/comment-collector/api/collect' \
  -H 'Content-Type: application/json' \
  -d '{
    "platformCode": "weibo",
    "featureCode": "comment",
    "targetId": "https://weibo.com/1644948230/NFxYz7abc",
    "excludedCapabilities": ["LOGIN_STATE"]
  }'
```

> 生效前提：`platform_feature_config.providers[].capabilities` 如实声明了能力
> （启动时 `ProviderCapabilityValidator` 会比对注解与配置的一致性）。

## 4. 接口详情

### 4.1 同步采集

一次性等待采集完成并返回**一页**结果。适用于"只要第一页"或调用方自己控制翻页的场景。
**不创建任务、不落库**。

```
POST /api/collect
Content-Type: application/json
```

请求体（`CommentCollectRequest`）：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `platformCode` | string | 是 | 平台编码 | `"wechat"` |
| `featureCode` | string | 是 | 功能编码 | `"comment"` |
| `targetId` | string | 是 | 目标 ID 或链接 | `"https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw"` |
| `maxCount` | int | 否 | 期望条数（当前不截断） | `20` |
| `userId` | string | 否 | 调用方用户 ID | `"user001"` |
| `userTierCode` | string | 否 | 用户等级：`ENTERPRISE` / `VIP` / `NORMAL`；不传按最低优先级 | `"VIP"` |
| `specifiedProviderKey` | string | 否 | 强制指定供应商，跳过路由 | `null` |
| `extra` | object | 否 | 供应商参数（见 §2.3） | `{"sort":"hot"}` |

**成功响应**（HTTP 200，`CommentCollectResult`）：

```json
{
  "success": true,
  "providerUsed": "wechat_sy",
  "taskId": null,
  "comments": [
    {
      "commentId": "15023660009290465290",
      "parentCommentId": null,
      "mid": null,
      "uid": null,
      "userName": "渐入佳境",
      "text": "我们不在一个城市，你的开心难过我看不见……",
      "time": "2021-04-08 22:01:31",
      "likeCount": 4,
      "replyCount": 0,
      "repostCount": null,
      "source": null,
      "ipLocation": "",
      "followCount": 0,
      "fansCount": 0,
      "statusCount": 0,
      "gender": null,
      "location": null,
      "description": null,
      "verifyType": null,
      "verifyInfo": null,
      "bigfans": null,
      "repostUrl": null,
      "insertTime": 1790134823083,
      "extra": null
    }
  ],
  "errorMessage": null,
  "hasMore": false,
  "nextCursor": null
}
```

**失败响应**（HTTP 200，`success=false`）：

```json
{
  "success": false,
  "providerUsed": null,
  "taskId": null,
  "comments": null,
  "errorMessage": "所有供应商均不可用: {bilibili_golaxy=供应商 [bilibili_golaxy] 返回失败状态: STATUS_ERROR}",
  "hasMore": false,
  "nextCursor": null

```

> `errorMessage` 会带出**每个候选供应商的真实失败原因**，便于定位是网络、Cookie 还是上游业务码问题。

字段说明：

| 字段 | 说明 |
|---|---|
| `success` | 本次采集是否成功（注意：成功但该页无评论时 `comments` 为空数组） |
| `providerUsed` | 实际使用的供应商 key |
| `hasMore` | 是否还有下一页 |
| `nextCursor` | 下一页游标；微博评论是 `maxId`、B站/小红书是 `cursor`、抖音/头条是页码、公众号/视频号是 `buffer` |

**curl 示例**

```bash

curl -X POST 'http://127.0.0.1:8075/comment-collector/api/collect' \
  -H 'Content-Type: application/json' \
  -d '{
        "platformCode": "wechat",
        "featureCode": "comment",
        "targetId": "https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw",
        "userId": "user001",
        "userTierCode": "VIP"
      }'
```

```bash
# B站评论，自己控制翻页：把上一页的 nextCursor 放进 extra.cursor
curl -X POST 'http://127.0.0.1:8075/comment-collector/api/collect' \
  -H 'Content-Type: application/json' \
  -d '{
        "platformCode": "bilibili",
        "featureCode": "comment",
        "targetId": "https://www.bilibili.com/video/BV1xx411c7mD",
        "extra": { "cursor": "1695000000000" }
      }'
```

```bash
# 微博评论（需要登录 Cookie）
curl -X POST 'http://127.0.0.1:8075/comment-collector/api/collect' \
  -H 'Content-Type: application/json' \
  -d '{
        "platformCode": "weibo",
        "featureCode": "comment",
        "targetId": "https://weibo.com/1234567890/N1234abcd",
        "specifiedProviderKey": "local_crawler",
        "extra": { "cookie": "SUB=xxx; SUBP=xxx; XSRF-TOKEN=abc123", "sort": "hot" }
```

### 4.2 创建异步采集任务

创建主任务并按链接拆分为子任务，**立即返回 taskId**；后台异步采集并把结果落库，
调用方用 §4.5 分页拉取结果。

```
POST /api/tasks
Content-Type: application/json
```

请求体（`TaskSubmitRequest`）：

| 字段 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `userId` | string | 否 | 用户 ID | `"user001"` |
| `userTierCode` | string | 否 | 用户等级，决定调度优先级 | `"VIP"` |
| `platform` | string | **是** | 平台编码（注意：异步接口字段名是 `platform`，不是 `platformCode`） | `"wechat"` |
| `function` | string | **是** | 功能编码（字段名是 `function`） | `"comment"` |
| `links` | string[] | **是** | 采集链接列表，一个链接一个子任务；**自动去重**，同一任务内重复链接只建一个子任务 | `["https://mp.weixin.qq.com/s/KtIy..."]` |
| `requestParams` | string | 否 | 供应商参数，**JSON 字符串**（见 §2.3） | `"{\"cookie\":\"SUB=xxx\"}"` |
| `supplierConstraint` | string | 否 | 供应商约束 | `null` |
| `callbackUrl` | string | 否 | 完成回调地址（主任务进入终态后 POST 结果摘要，见 §4.8） | `null` |
| `idempotencyKey` | string | 否 | 提交幂等键：同 key 重复提交返回已建成的 taskId，不重复建任务。建议用业务单据号等天然唯一值 | `"order-20261005-001"` |
| `autoPage` | boolean | 否 | 服务端自动翻页：`true` 采完一页自动续采下一页（受 `collector.task.auto-paging.max-pages` 限制）；`false` 一任务一页；缺省取全局默认（当前 `false`） | `true` |

**响应**：

```json
{ "success": true, "taskId": "MT1790135707593e62c3955", "totalLinks": 1 }
```

`/api/collect/async` 与 `/api/tasks` 等价，只是响应体为
`{"success":true,"taskId":"MT...","message":"任务已提交"}`。

**curl 示例**

```bash
curl -X POST 'http://127.0.0.1:8075/comment-collector/api/tasks' \
  -H 'Content-Type: application/json' \
  -d '{
        "userId": "user001",
        "userTierCode": "VIP",
        "platform": "wechat",
        "function": "comment",
        "links": [
          "https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw"
        ]
      }'
```

> 任务创建后**立即开始执行**（每个子任务单独提交到采集队列），主任务状态由
> `PENDING → ACTIVE → COMPLETED/FAILED` 自动收敛。

### 4.3 查询任务状态

```
GET /api/tasks/{taskId}
```

响应（`TaskQueryResponse`）：

```json
{
  "masterTaskId": "MT1790135707593e62c3955",
  "status": "COMPLETED",
  "links": [
    {
      "link": "https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw",
      "status": "SUCCESS",
      "supplier": "wechat_sy",
      "result": null,
      "subTaskId": "ST1790135707630c1f2a4b7",
      "errorMessage": null
    }
  ],
  "createTime": "2026-09-23T03:55:07.593Z",
  "updateTime": "2026-09-23T03:56:22.100Z",
  "totalLinks": 1,
  "successLinks": 1,
  "failedLinks": 0
}
```

| 字段 | 说明 |
|---|---|
| `status` | 主任务状态：`PENDING` / `ACTIVE` / `COMPLETED` / `FAILED` |
| `links[].status` | 子任务状态：`PENDING` / `RUNNING` / `RETRYING` / `SUCCESS` / `FAILED` |
| `links[].supplier` | 实际执行的供应商 key（未执行为 `null`） |
| `links[].result` | **当前恒为 `null`**；采集数据请用 §4.5 接口读取 |
| `links[].errorMessage` | 失败原因 |

任务不存在时返回 **HTTP 404**（无响应体）。

### 4.4 分页查询采集结果 ★ 核心

```
GET /api/tasks/{taskId}/comments?page=1&size=100&dataType=wechat_comment
```

### 4.5 队列状态

```
GET /api/queue/status
```

```json
{ "queueSize": 0, "queueCapacity": 10000, "queueRemaining": 10000, "overloaded": false }
```

| 字段 | 含义 |
|---|---|
| `queueSize` | 队列中**未完成任务总数**（Redis Stream HIGH+LOW 两条流未确认消息数，含消费者在途处理中的任务） |
| `queueCapacity` | 队列容量上限（`collector.task.queue-capacity`，可在 `/api/config` 动态调整） |
| `queueRemaining` | 剩余名额；为 0 时新的异步提交会被拒绝（503） |
| `overloaded` | `queueRemaining <= 0` 的便捷布尔 |

> ⚠️ **队列已外置 Redis Stream（阶段2）**：任务提交即写入流，进程重启后未完成任务仍在流里，
> 由消费者组（`collector-consumers`）继续消费，重启不丢任务。
> 容量在每条消息 XADD 时经 Lua 原子校验（HIGH+LOW 合计 ≤ 容量），严格不超卖；
> 消息处理完成才确认（XACK+XDEL），实例崩溃时未确认消息由其他实例/重启后的实例
> XCLAIM 接管重投 —— **至少一次投递**，子任务终态写入与主任务计数对重复投递幂等。
>
> `queueSize` 是全局真实积压量（不再有"各实例各自计数"的失真）。

### 4.8 完成回调（callbackUrl）

主任务进入终态（`COMPLETED` / `FAILED`）后，服务端向建任务时传入的 `callbackUrl`
POST 一条**结果摘要** JSON（不含评论数据）：

```json
{
  "taskId": "MT1790135707593e62c3955",
  "platformCode": "wechat",
  "featureCode": "comment",
  "status": "COMPLETED",
  "totalLinks": 3,
  "successLinks": 3,
  "failedLinks": 0,
  "completeTime": "2026-10-05T12:00:00Z"
}
```

投递语义（`collector.callback.*`）：

| 项 | 值 |
|---|---|
| 成功判定 | 响应 2xx |
| 重试 | 共 3 次（`collector.callback.max-attempts`），间隔 1s / 2s / 4s 退避 |
| 超时 | 单次 5000ms（`collector.callback.timeout-ms`） |
| 验签 | `collector.callback.secret` 非空时附加请求头 `X-Collector-Signature` = HMAC-SHA256(secret, body) 十六进制 |
| 失败后果 | **尽力而为**：重试耗尽后放弃并记 error 日志，不影响任务终态 |

> 回调只是"任务已结束"的通知；**不要**把收到回调当作数据唯一真相——
> 最终状态与数据一律以 `GET /api/tasks/{id}` 与 `GET /api/tasks/{id}/comments` 为准。

### 4.9 运行参数动态配置（system_config）

熔断阈值、限流参数、管线超时、重试退避、回调开关、自动翻页等**运行参数**已下沉到 MongoDB
`system_config` 集合（键名与 `application.properties` 属性路径同名，`_id` 即键）：

- **覆盖语义**：DB 有该键 → 以 DB 为准；没有 → 用 properties 默认。删除键 = 恢复默认。
- **生效延迟**：直接改 DB 最迟 60s（缓存 TTL）；走本组接口立即生效（淘汰缓存）。
- **种子数据**：`db/init-comment-collector.js` 用 `$setOnInsert` 播种全部默认键（不覆盖人工修改）。
- **不进 DB 的配置**：结构性参数（队列容量、消费者线程数、扫描周期）与安全敏感项
  （鉴权 API-Key、回调签名 secret）仍留在 properties/环境变量。

```
GET    /api/config                → 全部配置（键/值/说明/更新时间）
GET    /api/config/{key}          → 单个配置（404 = 未在 DB 配置，正在用默认值）
PUT    /api/config/{key}          → 写入配置（body: {"value":"60","description":"熔断时长（秒）"}）
DELETE /api/config/{key}          → 删除配置（回退 properties 默认）
```

常用键（完整清单见 `GET /api/config`）：

| 键 | 默认 | 说明 |
|---|---|---|
| `collector.circuit.open-seconds` | 60 | 熔断冷却时长（秒）——收紧/放宽熔断的高频运维项 |
| `collector.circuit.failure-rate-threshold` | 50 | 失败率熔断阈值（%） |
| `collector.pipeline.timeout-ms` | 15000 | 全局单次调用超时（毫秒），供应商配置优先 |
| `collector.pipeline.default-max-concurrency` | 4 | 全局默认并发上限（供应商配置优先） |
| `collector.pipeline.retry-backoff-base-ms` | 500 | 供应商内重试退避基数 |
| `collector.task.sub-retry-max` | 2 | 子任务级重投次数上限 |
| `collector.task.auto-paging.enabled` | false | 自动翻页全局默认 |
| `collector.task.auto-paging.max-pages` | 10 | 单链接最大翻页深度 |
| `collector.callback.enabled` | true | 完成回调开关 |

> 供应商接口使用频率（`rate_per_second`）、流控效果、并发上限等**每供应商**参数
> 本就在 `platform_feature_config.providers[]` 里（改后调用对应缓存淘汰接口或等 60s），
> 与本集合的**全局**参数分工：供应商级 → `platform_feature_config`，全局运行参数 → `system_config`。

## 5. 典型调用流程

### 5.1 同步取一页（最快）

```
POST /api/collect  →  直接拿到 comments，无需查库
```

### 5.2 异步多链接 + 分页拉结果（推荐）

```
① POST /api/tasks            →  { taskId }
② 轮询 GET /api/tasks/{id}    →  看 status 是否 COMPLETED（或先看 partial 数据）
③ GET /api/tasks/{id}/comments?page=1&size=100
   → total 即当前已落库总数；边跑边拉，不用等 COMPLETED
```

`jq` 版轮询脚本：

```bash
BASE='http://127.0.0.1:8075/comment-collector'
TASK=$(curl -s -X POST "$BASE/api/tasks" -H 'Content-Type: application/json' \
  -d '{"userId":"user001","userTierCode":"VIP","platform":"wechat","function":"comment",
       "links":["https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw"]}' | jq -r .taskId)
echo "taskId=$TASK"
while true; do
  ST=$(curl -s "$BASE/api/tasks/$TASK" | jq -r .status)
  N=$(curl -s "$BASE/api/tasks/$TASK/comments?size=1" | jq -r .total)
  echo "status=$ST 已落库=$N"
  [ "$ST" = "COMPLETED" ] || [ "$ST" = "FAILED" ] && break
  sleep 5
done
curl -s "$BASE/api/tasks/$TASK/comments?page=1&size=100" | jq '.total, (.data|length)'
```

### 5.3 持续翻页（自己控制游标）

```
① POST /api/collect  →  { comments, hasMore, nextCursor }
② 若 hasMore：
   把 nextCursor 按平台回填到 extra 的对应键（见下表），再次 POST /api/collect
③ 直到 hasMore=false
```

| 平台 | `nextCursor` 回填到 |
|---|---|
| 微博评论 / 微博转发 | `extra.maxId` / `extra.nextId` |
| B站 / 小红书 | `extra.cursor` |
| 抖音 / 今日头条 / 贴吧 / 荣耀/华为/OPPO 社区 | `extra.page`（页码） |
| vivo 社区 | `extra.lastId`（末条顶层/回复评论 id） |
| 小米社区 | `extra.cursor`（after：主列表=偏移量，回复=末条回复 id） |
| 公众号 / 视频号 | `extra.buffer` |

> 服务端每次调用只取一页（20 条），**翻页由调用方驱动**；这样调用方可以随时中断、限速或换存储。

### 5.4 混合平台一把梭（自动分派）

```
① POST /api/collect/dispatch      →  { dispatchId, tasks[] }
② 轮询 GET /api/dispatch/{id}     →  看 batchFinished / successLinks 汇总
③ 按 tasks[].taskId 调 GET /api/tasks/{taskId}/comments 分页拉各平台数据
```

适合链接来源不可控（用户上传/第三方推送）的场景；确定平台时仍推荐 #2 直接建任务，少一次识别。

## 6. 错误与状态语义

| 现象 | 含义 | 处理 |
|---|---|---|
| `POST /api/collect` 返回 `success=false` | 所有候选供应商都失败 | 看 `errorMessage` 里每个供应商的原因 |
| `errorMessage` 含 `返回失败状态: STATUS_ERROR` | 供应商拿到了响应但判定为失败（网络/上游业务码/解析失败） | 上游临时故障可重试；持续失败检查供应商配置 |
| `errorMessage` 含 `返回失败状态: STATUS_URL_ERROR` | 链接不支持（例如公众号非永久链接） | 换永久链接（`mp.weixin.qq.com/s/xxx`） |
| `errorMessage` 含 `缺少 Cookie` | 微博类供应商未传 `extra.cookie` | 补 `cookie` 字段 |
| `errorMessage` 含 `限流未获取到令牌` | 该供应商令牌桶已满（**含自适应降速后的低速率**） | 查 `supplier_state.effective_qps` / `adaptive_delay_ms`：可能是上游变慢触发了自动降速，属预期保护；也可提高 `ratePerSecond` 或改用 `flow_effect=THROTTLE_QUEUE` 让请求排队 |
| `errorMessage` 含 `Bean 未注册` | 配置里的 `providerKey` 与代码中的 Bean 名不一致 | 核对 `platform_feature_config.providers[].provider_key` |
| `errorMessage` 为 `当前无可用供应商，请稍后重试` | 该功能下**全部**候选都被熔断隔离或被运维下线 | 查 `supplier_state.circuit_state`（`OPEN` = 已熔断，会自动恢复）与 `platform_feature_config.providers[].is_healthy` |
| `errorMessage` 里**少了一个你以为会尝试的供应商** | 该供应商当前处于熔断 `OPEN`，被路由直接剔除，不会白打一次 | 正常行为；冷却结束后自动半开探测恢复 |
| `GET /api/tasks/{id}` 返回 404 | taskId 不存在 | — |
| `GET /api/tasks/{id}/comments` 返回 `total=0` 且任务仍在跑 | 还没采到数据 | 继续轮询 |
| `POST /api/tasks` 返回 400 `links不能为空` | `links` 缺失或为空数组 | — |
| `POST /api/tasks` 返回 400 `MALFORMED_BODY` | 请求体结构不对，最常见的是 `requestParams` 传成了 JSON **对象** | 该字段是 **JSON 字符串**，要传 `"{\"url\":\"...\"}"`；错误信息会直接点名出错字段 |
| `POST /api/tasks` 返回 **503** `SERVICE_BUSY` | 服务过载：异步队列名额不足 | **可重试**（两个应当重试的错误码之一）。退避后重试；可用 `GET /api/queue/status` 观察排队情况。被拒请求**不会产生任何任务记录**，可整批重试 |
| `POST /api/collect` 返回 **503** `PROVIDER_UNAVAILABLE` | **指定了 `specifiedProviderKey` 且该供应商调用失败**（超时 / 熔断 OPEN / 并发上限满 / 限流未取到令牌 / 上游返回失败） | **可重试**（两个应当重试的错误码之一）。响应体额外带 `providerKey` 与 `reason`（异常类名）供定位；`reason` 取值见下表 |
| `errorMessage` / `message` 含 `并发已达上限（在途 N，上限 M），不再排队` | 该供应商的在途调用已达 `providers[].max_concurrency`（Bulkhead 快速失败，**不排队**） | 立即重试意义不大；降低并发、调大 `max_concurrency`，或改用候选列表路径让中间件自动切换 |
| 含 `处于熔断状态（OPEN），本次不发起调用` | 执行前闸门拦截，**没有发起这次调用** | 等冷却（`collector.circuit.open-seconds`）后自动半开探测；持续出现说明上游确实故障 |
| 含 `单次调用超时（> Nms）` | 单次尝试超过 `providers[].timeout_ms`（或全局 `collector.pipeline.timeout-ms`） | 重试有用（上游慢）；持续则调大超时或降低并发 |
| 含 `调用链总预算耗尽（Nms 内已尝试 M 次）` | 整条重试链的墙钟预算 `timeout×(max_retry+1)+退避总和` 已用完 | 说明上游持续超时，重试只会更慢；先排查上游 |
| 含 `限时线程池已满` | 管线限时线程池（`collector.pipeline.timeout-threads`）打满 | 服务侧容量问题，按 503 处理并退避重试 |
| 任意接口返回 405 / 415 | HTTP 方法或 `Content-Type` 用错 | 保留框架语义，按提示改正 |

**503 的 `reason` 取值**（仅 `PROVIDER_UNAVAILABLE` 有）：

| `reason` | 含义 |
|---|---|
| `ProviderInvocationException` | 供应商执行失败（含重试耗尽、熔断闸门拒绝、上游返回失败状态、限时线程池满） |
| `BulkheadFullException` | 并发上限已满，快速失败未排队 |
| `ProviderTimeoutException` | 单次调用超时或整链预算耗尽 |
| `RateLimitedException` | 未取到令牌（含自适应降速后的低速率） |

> **为什么候选列表路径不返回 503，而指定供应商路径返回 503**：候选路径下中间件已经尽力在多个供应商之间切换，失败是"业务上没采到"（`200 + success=false` + 逐供应商原因）；而调用方**点名**了某个供应商时，失败属于"它现在不行、稍后可能行"，返回 503 才能让调用方/网关的自动重试机制生效。

> 业务失败返回 **HTTP 200**（用 `success` / `status` 字段表达）；参数/请求体问题返回 **400**；过载返回 **503**（`SERVICE_BUSY`），指定供应商失败返回 **503**（`PROVIDER_UNAVAILABLE`）。
> 统一错误体：`{"success":false,"code":"...","message":"...","error":"...","timestamp":"..."}`
> （`error` 为兼容历史字段保留，与 `message` 同值；`SERVICE_BUSY` 额外带 `queueSize`/`queueCapacity`/`queueRemaining`，`PROVIDER_UNAVAILABLE` 额外带 `providerKey`/`reason`）。

## 7. 常量与边界

| 项 | 值 | 来源 |
|---|---|---|
| 单供应商单页条数 | 20 | 各上游接口固定值 |
| 供应商内部 HTTP 重试 | 3 次，间隔 1s（`HttpUtil` 自带） | 各 Provider 实现 |
| 框架级重试（换供应商前） | 由 `platform_feature_config.providers[].max_retry` 决定；**与上面 3 次内部重试叠乘** | MongoDB 配置 |
| 单次调用超时 | 15000ms（`providers[].timeout_ms` 优先；`0` = 不限） | `collector.pipeline.timeout-ms` |
| 调用链总预算 | `单次超时 × (max_retry+1) + 退避总和`（退避 = 500 × 2^(n-1)） | `InvocationContext.totalBudgetMs()` |
| 供应商并发上限（Bulkhead） | 默认 4（`providers[].max_concurrency` 优先；`0` = 不限）；**满了立即失败，不排队** | `collector.pipeline.default-max-concurrency` |
| 网络层兜底截止线 | 60s（OkHttp `callTimeout`）；**管线超时应小于它**，否则底层请求会活得比这里更久 | `http-client-utils` 默认值 |
| 供应商有效速率 | `min(rate_per_second, 1000/adaptive_delay_ms)`，上游变慢时自动下降（下限 `start_delay_ms`=500ms ⇒ 最高 2/s）；**令牌桶/延迟/预热起点均在 Redis，多实例共享同一份配额**（阶段2） | 分布式令牌桶，见设计文档 §8.2 |
| 取令牌等待（`REJECT`/`WARM_UP`） | 500ms，超时即跳过该供应商 | `collector.ratelimit.reject-timeout-ms` |
| 取令牌等待（`THROTTLE_QUEUE`） | 默认 2000ms，可被供应商的 `max_queue_wait_ms` 覆盖 | 设计文档 §8.3 |
| 异步队列容量 | 10000，HIGH+LOW 两流未确认消息总数上限，满则新提交返回 503；XADD 内 Lua 原子校验，严格不超卖；可经 `/api/config` 动态调整 | `collector.task.queue-capacity` |
| 队列实现 | **Redis Stream 外置队列**（HIGH/LOW 双流两级优先级 + 消费者组），重启不丢任务；处理完成 XACK+XDEL，崩溃遗留消息 XCLAIM 接管（至少一次投递） |
| Redis 降级兜底 | Redis 故障时**服务不停摆**：任务落本地兜底队列由本实例消化、熔断/限流按放行兜底、启动不因 Redis 失败而失败；探活恢复后自动重建消费组并回流兜底队列。兜底队列是内存态——降级期间进程崩溃由启动恢复扫描兜底 | `collector.queue.redis-probe-ms` 等 |
| deadline 保障 | LOW 流中等待超过 30 分钟（`collector.task.max-wait-minutes`）的任务由维护任务迁移到 HIGH 流 | `collector.queue.promotion-scan-ms` |
| 分页 `size` 上限 | 1000 | 接口内限制 |
| 供应商级重试（同一家内部） | 见上"供应商内部 HTTP 重试"与"框架级重试"两行，重试发生在**单次执行内** | — |
| 子任务级重投（跨队列） | 默认 2 次（`collector.task.sub-retry-max`），指数退避 2s 起步、封顶 10min；全部候选供应商耗尽且失败非确定性（链接不支持/Bean 未注册等不重投）时才触发，由后台扫描 `RETRYING` 子任务重投 | `collector.task.sub-retry-*` |
| 评论落库幂等 | `_id = taskId-mid-commentId`，同任务重采同一条评论为覆盖写（保留最新），不会产生重复行 | `CommentDoc` 业务主键 |

## 8. 数据模型（结果字段）

采集结果统一落在 MongoDB 集合 `comment`，用 `dataType` 区分类型。字段含义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 业务主键 `{taskId}-{mid或链接}-{commentId}`，重复采集同一评论为**覆盖**而非新增 |
| `taskId` / `subTaskId` | string | 所属主任务 / 子任务 |
| `dataType` / `platformCode` / `providerKey` | string | 类型 / 平台 / 实际供应商 |
| `fromUrl` | string | 采集来源链接 |
| `mid` | string | 内容 ID（微博 mid、视频 ID 等） |
| `commentId` / `parentCommentId` | string | 评论 ID / 父评论 ID |
| `uid` / `userName` | string | 评论者 ID / 昵称 |
| `text` | string | 评论正文 |
| `time` | string | 评论时间（`yyyy-MM-dd HH:mm:ss`） |
| `likeCount` / `replyCount` / `repostCount` | int | 点赞 / 回复 / 转发数 |
| `source` / `ipLocation` | string | 来源 / IP 属地 |
| `followCount` / `fansCount` / `statusCount` | long/int | 关注 / 粉丝 / 发文数（微博） |
| `gender` / `location` / `description` / `verifyType` / `verifyInfo` / `bigfans` | string | 微博用户扩展信息 |
| `repostUrl` | string | 转发者微博地址（微博转发） |
| `insertTime` | long | 落库时间戳（毫秒） |

> 平台没有的字段会是 `null`（例如公众号评论没有 `mid` / `followCount`）。

## 10. 快速自测清单

```bash
BASE='http://127.0.0.1:8075/comment-collector'

# 1) 存活
curl -s "$BASE/api/health"

# 2) 同步采集（公众号文章）
curl -s -X POST "$BASE/api/collect" -H 'Content-Type: application/json' \
  -d '{"platformCode":"wechat","featureCode":"comment",
       "targetId":"https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw"}' | jq '.success,.providerUsed,(.comments|length)'

# 3) 异步任务 + 结果分页
TASK=$(curl -s -X POST "$BASE/api/tasks" -H 'Content-Type: application/json' \
  -d '{"userId":"u1","userTierCode":"VIP","platform":"wechat","function":"comment",
       "links":["https://mp.weixin.qq.com/s/KtIy4UdYzUvdLUFIfrmmDw"]}' | jq -r .taskId)
sleep 60
curl -s "$BASE/api/tasks/$TASK" | jq '.status,.successLinks'
curl -s "$BASE/api/tasks/$TASK/comments?size=3" | jq '.total'
```
