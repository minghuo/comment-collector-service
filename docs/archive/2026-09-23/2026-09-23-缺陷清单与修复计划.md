## 0. 结论摘要

1. **项目当前不可构建、不可启动。** 实测 `mvn clean compile` 失败，`24 errors`，全部集中在 `WeiboComment.java`
   （依赖 `cn.idev.excel`，`pom.xml` 未声明该依赖）；即使补上依赖，启动阶段仍会因
   **SLF4J/log4j 绑定冲突**与**默认 profile 占位符缺失** 失败。
2. **核心业务链路断裂。** `/api/collect/async` 与 `/api/tasks` 创建的任务**只落库、无人执行**，
   子任务状态永远停留 `PENDING`；即使被打通，供应商返回 `STATUS_ERROR` 也会被判定为成功，
   重试与供应商切换全部失效；评论解析是空壳（整段 JSON 塞进 `id`/`content`）。
3. **两份需求文档 + 一份设计文档均存在与实现冲突的事实性错误。** 已全部修订为 v1.1，
   并把"未实现项"从需求中显式剥离（含 R-01～R-27、C-01～C-16、D-01～D-32 共 75 处勘误）。
4. 本计划按 **P0（可运行）→ P1（主链路）→ P2（调度正确性）→ P3（可靠性）→ P4（工程化）→ P5（生产就绪）**
   分阶段给出可直接执行的改动点、验收方法与依赖关系。

## 3. 代码缺陷清单（40 项，按严重度排序）

> 每条给出：现象 → 证据（文件:行） → 影响 → 修复方向

### 3.1 🔴 阻断级（不修则项目无法运行 / 功能完全不可用）

#### C-01 项目编译失败：`WeiboComment` 依赖缺失
- **现象**：`mvn compile` 24 errors。
- **证据**：`src/main/java/com/sysj/collector/model/WeiboComment.java:4-5` `import cn.idev.excel.annotation.{ExcelIgnore,ExcelProperty}`；
  `pom.xml` 全文无 `cn.idev.excel` / `com.alibaba.excel` / `excel-utils` 依赖。
- **影响**：整个模块不可构建。
- **修复方向**（二选一）：
  - **(推荐) 删除 `WeiboComment.java`**。它：① 未被任何 Provider/Controller 引用（纯死代码）；
    ② 是 `auto-task-web` 的复制品，带 `@Document(collection="weibo_comment")` 但无人写入；
    ③ 它引入的 `cn.idev.excel` 注解只服务于 Excel 导出，而本服务是**采集中间件，不做导出**；
    ④ 它还把 Excel/`com.bewilder.weibo.WeiboTool` 等无关耦合带进来。
  - 或在 `pom.xml` 补 `cn.idev.excel:fastexcel`（需确认 groupId/版本，属未核实值）。

#### C-02 应用启动失败：SLF4J / log4j 绑定冲突
- **现象**：`log4j-slf4j-impl` 与 `log4j-to-slf4j` 共存，启动时 `LoggingException: log4j-slf4j-impl cannot be present with log4j-to-slf4j`。
- **证据**：`mvn dependency:tree` 显示三条同时存在；
  `log4j-slf4j-impl-2.24.3.jar` 的 `org/apache/logging/slf4j/Log4jLoggerFactory.class` 常量池含该字符串；
  `pom.xml:27-31` 的 `spring-boot-starter-web` **未排除** `spring-boot-starter-logging`；
  `bewilder-tools` 的 pom 声明了 `log4j-core` + `log4j-1.2-api` + `log4j-slf4j-impl` 为 compile 依赖。
- **影响**：应用无法启动。
- **修复方向**（二选一，写进 README）：
  - **(推荐) 保留 Logback**：在 `bewilder-tools` 依赖上 `<exclusions>` 排除
    `org.apache.logging.log4j:log4j-slf4j-impl`、`log4j-core`、`log4j-1.2-api`；删除 `src/main/resources/log4j2.xml`。
  - **全量切 Log4j2**：`spring-boot-starter-web` 排除 `spring-boot-starter-logging`，引入 `spring-boot-starter-log4j2`，重写 `log4j2.xml`。

#### C-03 应用启动失败：默认 profile 缺少必需占位符
- **证据**：`config/MongoConfig.java:24-34` 强依赖 `mark.uri`/`sq.uri`/`auto_task.uri`/`hot_rank.uri`；
  `config/CommonConfig.java:16,23,31` 强依赖 `file.upload.dir.permission`/`file.upload.dir.path`/`interact.apiUrl`；
  这些键**只**出现在 `application-dev.properties` / `application-pro.properties`；
  `application.properties` 无 `spring.profiles.active`。
- **影响**：`Could not resolve placeholder 'mark.uri'` → 启动失败。
- **修复方向**：见 C-27（删除 `CommonConfig` 无关配置）与 C-10（删除多数据源）。

#### C-04 Java 版本声明矛盾
- **证据**：`pom.xml:18-19` `maven.compiler.source/target=21`；`pom.xml:112-113` 插件配置 `17`（插件配置优先）；
  实测构建日志 `release 17`。
- **影响**：Java 21 特性不可用；团队对目标版本认知不一致。
- **修复方向**：删除插件里的 `17`，统一由 `spring-boot-starter-parent` 的 `java.version` 或
  `<maven.compiler.release>21</maven.compiler.release>` 单一来源控制。

#### C-13 异步任务链路断裂（最高优先级功能缺口）
- **现象**：`POST /api/collect/async` 与 `POST /api/tasks` 只创建 `master_task` + `sub_task` 记录，
  **没有任何组件消费 `sub_task`**。
- **证据**：
  - `controller/CommentController.java:62-73, 95-105` 只调用 `taskManagementService.createMasterTask(...)`；
  - `domain/service/TaskManagementService.java:72-106` 只做 `save` + `splitIntoSubTasks` + `saveAll`；
  - `facade/CommentCollectionFacade.java` 的异步队列消费的是 `CommentCollectRequest`（内存对象），
    与 `SubTask` **没有任何关联字段**；
  - `TaskManagementService.updateSubTaskStatus` / `updateMasterTaskStatus`（`:123, :145`）**无任何调用方**（全局 grep 确认）。
- **影响**：所有异步任务永远 `PENDING`，采集结果永远为空。
- **修复方向**（架构决策点，见 §4 方案 A/B）：让 `SubTask` 成为一等执行单元，
  执行前 `SubTask(id, link, providerKey, extra…) → CommentCollectRequest`，执行后原子回写 `result/status`；
  `MasterTask` 计数在子任务终态时收敛。

#### C-05 评论解析是空壳
- **证据**：`model/Comment.java:32-37`
  ```java
  public static Comment buildFromGolaxy(String jsonStr) {
      return Comment.builder().id(jsonStr).content(jsonStr).build();   // 整段 JSON 塞进两个字段
  }
  ```
  所有 Golaxy Provider（Bili/Douyin/Xhs）与头条 Provider 都调用它 / 类似的 `parseComment`。
- **影响**：即使链路打通，返回的评论除 `id`/`content`（都是原始 JSON 串）外**全部字段为空**。
- **修复方向**：按设计文档 §3.6 的映射表实现真实解析（PARSE 逻辑照搬 `auto-task-web` 的
  `BiliComment.buildFromGolaxy` / `DyComment.buildFromGolaxy` / `XhsComment.buildFromGolaxy` / `TtComment.build`）。

#### C-06 供应商失败被判定为成功 → 重试/切换全失效
- **证据**：
  - `CommentProvider` 接口契约（`core/provider/CommentProvider.java:29-31`）是"失败时直接抛出异常"；
  - 但 4 个真实 Provider 在失败时**返回** `STATUS_ERROR` 而非抛异常：
    `BiliGolaxyCrawlerProvider.java:83,116`、`DouyinGolaxyCrawlerProvider.java:79,105`、
    `XhsGolaxyCrawlerProvider.java:79,107`、`TouTiaoLocalCrawlerProvider.java:85,116`；
  - `facade/CommentCollectionFacade.java:345-353` 只 `try/catch`，**不检查 `result.getStatus()`**，
    直接 `success(true)` 并返回 `result.getDataList()`（可能为 null → 空列表）。
- **影响**：HTTP 失败 → 不重试、不切换供应商 → 接口返回 `success=true` + 空评论列表；观测上完全误导。
- **修复方向**：在 `executeProviderWithSwitch` / `executeProviderRetry` 中，
  若 `result == null || result.getStatus() != CommonStatusEnum.STATUS_SUCCESS` 则视为失败（抛异常或走失败分支）。
  **同时**把该口径写进设计文档 §7 与需求文档 §3.6。

#### C-07 异步消费异常吞掉，调用方永久挂起
- **证据**：`facade/CommentCollectionFacade.java:145-167`
  ```java
  CommentCollectResult result = doCollect(task.request());
  task.future().complete(result);          // 只有正常返回才 complete
  ...
  } catch (Exception e) {
      log.error("异步任务执行异常", e);     // 异常时 future 永不完成
  }
  ```
  `doCollect` 中 `configService.loadFeatureConfig(...)` 在功能不存在时抛 `CollectorException`。
- **影响**：`collectAsync` 的调用方（含 `TaskRecoveryService`）**永久阻塞**，线程/连接泄漏。
- **修复方向**：`catch` 分支补 `task.future().completeExceptionally(e)`；
  并给 `collectAsync` 增加超时（如 `orTimeout`）。

#### C-10 `MongoTemplate @Primary` 指向错误数据库
- **证据**：`config/MongoConfig.java:40-44`
  ```java
  @Primary
  @Bean(name = "markMongoTemplate")
  public MongoTemplate getMarkMongoTemplate() { return initMongoTemplate(markUri); }   // mark.uri → qbjc 库
  ```
  `domain/service/ProviderConfigService.java:40,107,124` 注入裸 `MongoTemplate` → 拿到 `markMongoTemplate`。
- **影响**：`updateProviderHealth` / `updateProviderRate` 会写到 `qbjc` 库（生产事故级）；
  而 Repository 走 `spring.data.mongodb.uri`（`comment_collector` 库）→ 读写分库。
- **修复方向**：删除 `MongoConfig` 多数据源（本服务只用 1 个库），改用 Spring Boot 自动配置的 `MongoTemplate`；
  若确需多数据源，所有注入点显式 `@Qualifier`。

#### C-11 命名策略与手写字段名不匹配
- **证据**：`config/MongoConfig.java:66-67` 设置 `SnakeCaseFieldNamingStrategy`（落库为 `platform_code`/`provider_key`/`is_healthy`）；
  但：
  - `domain/document/PlatformFeatureConfig.java:47` `@CompoundIndex(def = "{'platformCode': 1, 'featureCode': 1}")` → 索引建在不存在字段；
  - `domain/service/ProviderConfigService.java:102-106`
    `Criteria.where("platformCode")…and("providers.providerKey").is(providerKey)` + `set("providers.$.isHealthy", …)` → **永远匹配不到**。
- **影响**：健康/限流热更新的运维操作**静默失效**（`updateFirst` 更新 0 条不报错）；唯一索引未生效。
- **修复方向**（二选一）：
  - **(推荐)** 放弃 `SnakeCaseFieldNamingStrategy`，改用 `@Field("platform_code")` 显式声明（可读、可校验）；
  - 或保留策略，把所有手写字面量改为下划线名。

### 3.2 🟠 高危（功能错误 / 数据不一致）

#### C-08 防饥饿机制实际失效
- **证据**：`facade/CommentCollectionFacade.java:437-467`。
  `PrioritizedTask.setAgingBoost()`（`:457-460`）与 `setEffectivePriority()`（`:461`）只改 volatile 字段，
  而它被放入 `PriorityBlockingQueue`（`:71-72`）——**PBQ 只在插入/删除时堆化，元素内部优先级变化后不会重排**。
  aging 定时器（`:226-254`）每 30s 改字段，但队列位置不变。
- **影响**：`aging-priority-boost` / `max-wait-minutes` / Deadline 保障**全部形同虚设**，低优先级任务可被无限饿死。
- **修复方向**（三选一，需在 §4 决策）：
  - (a) 出队后重算有效优先级，若已提升则重新 `offer` 回去；
  - (b) 改用 `DelayQueue` + 动态延期；
  - (c) 取消内存 PBQ，改为每次调度从 `sub_task` 按 `effectivePriority` 查询排序（与 C-13 的重构合并最省事）。

#### C-09 公平配额实现错误
- **证据**：`facade/CommentCollectionFacade.java:176-222`
  - "高优先级"硬编码 `t.priority() < 500`（`:178`），无配置来源；
  - `fairRoundActive` / `fairRoundProcessed` 是**实例级共享状态**（`:85-86`），多个消费者线程会互相干扰；
  - `batchSize = (int)(total * fairQuotaRatio)`（`:189`）语义与文档"每消费周期 30% 处理能力"不符。
- **影响**：公平模式可能反向导致高优先级被饿死，或完全失效。
- **修复方向**：改为线程本地计数 / 配额令牌；`500` 改配置项；轮次结束条件改为"低优先级队列已空 或 配额用尽"。

#### C-12 健康状态读写分裂
- **证据**：
  - 写：`core/router/DynamicProviderRouter.java:221-242` `markProviderFailure()` → `supplier_state.health_status = "DOWN"`；
  - 读：`facade/CommentCollectionFacade.java:285-287` 读的是 `ProviderConfig::isHealthy`（`platform_feature_config`）；
  - 全局 grep 确认 `supplier_state` **没有任何读取方**，也没有恢复代码。

## 4. 关键架构决策点（需要你先拍板）

以下两项决定后续所有改动的形态，建议优先确认：

### 决策 1：异步任务的执行载体（对应 C-13 / C-14 / C-08）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 内存队列为主（现状延续）** | `collectAsync` 直接入 PBQ；`sub_task` 仅作审计记录，结果异步回写 | 改动最小 | 队列不持久化，重启丢任务；aging 需修 PBQ 重排（C-08）；集群不可用 |
| **B. 以 `sub_task` 为工作队列（推荐）** | 调度循环周期性从 `sub_task` 拉 `PENDING`（按 `effective_priority` 排序、`next_execute_time <= now`）→ 原子置 `RUNNING` → 执行 → 回写 | 天然持久化、天然支持多实例（配合原子抢占）、aging 在 SQL/查询层解决、恢复流程自然闭环 | 改动量大；需要索引与原子更新（C-30/C-32） |
| C. 引入 MQ | 子任务投递到 RabbitMQ/Kafka | 解耦彻底 | 引入新中间件，超出本期范围 |

> **建议选 B**：它一次性解决 C-08（不再依赖 PBQ 重排）、C-13、C-14、C-32，并与需求文档的
> "子任务由调度器扫描 PENDING 并分配供应商"（需求 §7.2）完全一致。方案 A 会在 P2 阶段再次推倒重来。

### 决策 2：日志体系（对应 C-02 / C-26）

| 方案 | 做法 |
|---|---|
| **A. 保留 Logback（推荐）** | 排除 `log4j-slf4j-impl`/`log4j-core`/`log4j-1.2-api`，删除 `log4j2.xml` |
| B. 全量切 Log4j2 | 排除 `spring-boot-starter-logging`，引入 `spring-boot-starter-log4j2`，重写 `log4j2.xml` |

> **建议选 A**：改动最小，且与 Spring Boot 默认一致。`auto-task-web` 用 Log4j2 是它的历史选择，本服务无必要跟随。

### 决策 3（次要）：`WeiboComment` 去留（对应 C-01 / C-34）

建议**删除**（理由见 C-01）。若近期要做 Excel 导出，则应把它移到独立模块并补齐 excel 依赖，而不是留在采集服务里。

## 6. 依赖关系与建议执行顺序

```
P0（可运行）
  └─▶ P1（主链路）─┬─▶ P2（调度正确性）
                   │        └─▶ P3（可靠性）
                   │                 └─▶ P4（工程化）
                   │                          └─▶ P5（生产就绪）
                   └─▶（P1-1 解析、P1-2 失败判定可与 P0 并行准备）
```

- **P0 与 P1 的部分工作可并行**：P1-1（解析）、P1-4/P1-5/P1-6（Provider 内部质量）不依赖 P0 的构建修复，可先写代码后统一验证。
- **P2-5（防饥饿）依赖决策 1**：若选方案 B，P2-5 与 P1-8 合并实施，工作量可省约 1 天。
- **P3 必须在 P2 之后**：幂等与原子更新依赖 P2-8 的索引与 P2-1 的路由收口。
