## 1. 项目概述

### 1.1 项目背景

业务需要从多个社交平台批量采集评论数据，并预留互动指标更新、账号历史等扩展能力。
每个平台存在多个数据供应商（官方 API、第三方服务、自研爬虫），在成本、速率、稳定性上存在差异，
需要统一的中间服务实现供应商的灵活调度、优先级路由、故障切换及资源公平分配。

### 1.2 项目目标

- `[部分实现]` 构建高可用、可扩展的采集中间服务，屏蔽底层多供应商差异。
- `[部分实现]` 支持动态配置多平台、多供应商的优先级、频次、健康状态。
- `[部分实现]` 实现基于任务量和用户优先级的智能路由，防止资源饥饿。
- `[部分实现]` 提供即时返回与异步任务两种模式。
- `[未实现]` 支持断点续采。
- `[已实现]` 支持未来新增业务类型而不改动核心路由逻辑（通过 `featureCode` 配置化）。

### 1.3 本期范围（v1.1 收紧）

- **包含**：多平台评论采集（微博、抖音、小红书、B站、今日头条）的**任务创建、供应商路由、限流、重试与切换、结果返回**。
- **不含**：具体爬虫解析逻辑（由各供应商实现类承担）、管理后台、鉴权、集群化。
- **明确移出**：微信（无实现）、互动指标更新、账号历史。

> **修订（C-14）**：v1.0 声称"不包括具体爬虫实现"，但当前代码里供应商实现类**同时承担了 HTTP 调用与 JSON 解析**，
> 属于实现层职责。v1.1 明确：供应商实现类**负责**调用与解析，框架层只负责路由/限流/重试/切换。
> 这也意味着"新增供应商无需改代码"不成立 —— 新增供应商必须新增实现类（见总体需求 §3.2）。

## 2. 术语定义

| 术语 | 说明 |
|---|---|
| 平台 | 社交媒体平台，`platformCode` ∈ {`weibo`, `douyin`, `xhs`, `bilibili`, `toutiao`} |
| 功能 | 具体业务，`featureCode`，本期仅 `comment` |
| 供应商 | 实现某一平台某一功能的数据提供方，由 `providerKey` 标识，**必须与 Spring Bean 名一致** |
| 主任务 | 由用户提交的一个完整采集请求，关联一个或多个采集对象（链接） |
| 子任务 | 将主任务按链接拆分的执行单元，由调度器分配给具体供应商执行 |
| 即时返回（SYNC） | 同步等待采集结果并直接返回给用户 |
| 任务模式（ASYNC） | 接受请求后返回任务 ID，异步执行，用户通过查询接口获取结果 |
| 阈值 | 触发启用低优先级供应商的任务队列长度设定（`activationThreshold`） |
| 用户优先级 | 标识用户重要程度的等级（`user_tier_config.priority`），**数值越小越优先** |

## 3. 功能性需求

### 3.1 多平台与多供应商管理

- **FR-01** `[已实现]` 系统支持注册多个平台，每个平台可配置多种功能（集合 `platform_feature_config`）。
- **FR-02** `[已实现]` 每个功能下可管理多个供应商，配置项：

  | 配置项 | 类型 | 说明 | 状态 |
  |---|---|---|---|
  | 供应商唯一标识 `providerKey` | String | 与 Spring Bean 名一致 | `[已实现]` |
  | 请求频次上限 `ratePerSecond` | double | 许可数/秒 | `[已实现]` |
  | 最大重试次数 `maxRetry` | int | 首次调用不计入 | `[已实现]` |
  | 健康状态 `isHealthy` | boolean | **人工标记**，非探活 | `[部分实现]` |
  | 优先级 `priority` | int | **数值越小越优先** | `[已实现]` |
  | 是否支持即时返回 | boolean | 接口无该字段 | `[未实现]` |
  | 单次最大处理链接数 | int | 无该字段 | `[未实现]` |

- **FR-03** `[部分实现]` 供应商配置支持运行时动态加载与更新（MongoDB + Caffeine TTL 60s）。
  **缺对外刷新接口**，改库后最长 60s 生效。
- **FR-04** `[未实现]` 健康检查机制：定期探活、连续失败自动降级、恢复自动上线。

> **修订（C-06）**：优先级方向统一为**数值越小越优先**（供应商 `priority` 与用户 `priority` 同向）。
> **修订（C-08）**：v1.0 要求 15s 探活 + 自动降级/恢复，当前实现完全没有。本期改为"运维手工标记 `isHealthy`"，
> **且手工标记后无自动恢复路径**。

### 3.2 优先级与阈值路由

- **FR-05** `[已实现]` 任务按 `platformCode + featureCode` 路由到对应供应商列表。
- **FR-06** `[部分实现]` 默认按供应商 `priority` 升序分配。
  - ⚠️ 实现**不对列表排序**，直接按 MongoDB 数组物理顺序遍历；文档承诺的"写入时保证有序"无代码保障。
- **FR-07** `[部分实现]` 按任务队列深度设置阈值：待处理任务数 `>= activationThreshold` 时启用次优先供应商分流。
  - ⚠️ 该阈值定义于 `user_tier_config`，且**在门面调用路径上未生效**（仅死代码 `DynamicProviderRouter.route()` 使用）。
- **FR-08** `[已实现]` 特定指标需求时，可由调用方指定必须使用的供应商（`specifiedProviderKey`），绕过全局优先级。
- **FR-09** `[已实现]` 供应商 `isHealthy=false` 时自动将新任务分配给次优先可用供应商；正在执行的任务失败后按重试策略处理。

**优先级示例（微博评论）**：`weibo_official`(priority=10) → `local_crawler`(priority=20)。
> **修订**：v1.0 示例写「本地爬虫(1) > A公司接口(2) > 微博官方(3)」，其中"A公司接口"当前无实现类。

### 3.3 用户优先级与资源分配

- **FR-10** `[已实现]` 系统维护用户等级（`user_tier_config`），`priority` 数值越小越优先。
- **FR-11** `[部分实现]` 多用户同时调用同一功能时，按用户优先级 + 提交时间分配执行机会。
  - 实现为 `PriorityBlockingQueue`，但**优先级变更后不重排**（见 FR-13 缺陷）。
- **FR-12** `[部分实现]` 高优先级用户可优先使用高优供应商：由 `providerOrder` 覆盖全局顺序。
  - v1.0 的"低优先级用户起始供应商列表限制在较低优先级区间"当前**无对应字段**（只能通过 `providerOrder` 子集近似表达）。
- **FR-13** `[部分实现]` 防止高优任务阻塞低优任务：等待超过阈值临时提升优先级。
  - 阈值：`collector.task.max-wait-minutes`（默认 30min，非 v1.0 所述的"初始 30 分钟、支持动态调整"——当前**不可运行时调整**）。
  - ⚠️ **缺陷**：优先队列元素优先级变更后不重排，提升实际不生效。

### 3.4 任务提交与路由

- **FR-14** `[已实现]` 用户通过 RESTful API 提交主任务，包含平台、功能、链接列表（支持批量）、返回模式、可选供应商约束。
- **FR-15** `[未实现]` 入参校验（平台存在、功能存在、链接格式）。当前 `@Valid` 无任何约束注解，形同虚设。
- **FR-16** `[已实现]` 生成主任务记录并按链接拆分为多个子任务。
  - v1.0 的"根据**供应商能力**拆分"当前无实现（无 `maxBatchLinks` 概念，1 链接 = 1 子任务）。
- **FR-17** `[未实现]` 子任务进入有序队列并由调度器消费。
  - 现状：子任务仅落库为 `PENDING`，**无任何消费者**（🔴 阻断级缺口）。

### 3.5 采集模式

- **FR-18 即时返回模式** `[已实现]`
  - 同步等待执行完成后返回结果。
  - **v1.1 修订**：v1.0 的"仅当所有选定供应商都支持即时返回且链接数较少时允许"当前**无实现依据**
    （`CommentProvider` 接口无 `supportsSync()`，也没有链接数上限校验）。
  - **v1.1 修订**：v1.0 的"支持超时控制，超时后降级为任务模式" `[未实现]`。
  - **v1.1 修订**：v1.0 的"无需持久化子任务"与实现一致，但需明确**SYNC 路径不产生任何任务记录**。
- **FR-19 任务模式** `[部分实现]`
  - `[已实现]` 提交后立即返回主任务 ID。
  - `[已实现]` 用户通过任务查询接口获知完成状态。
  - `[未实现]` 实际后台采集执行。

### 3.6 断点续采与重启恢复

- **FR-20** `[部分实现]` 重启时自动恢复未完成的主任务及其子任务。
  - 已实现：扫描 + 重置状态 + 重新入队。
  - **缺陷**：入队请求不携带 `subTaskId`，返回值被丢弃 → **结果无法回写，恢复后子任务状态永远不变**。
- **FR-21** `[部分实现]` 执行中的子任务在重启时标记为中断并按重试策略重新入队。
  - 实现为「`RUNNING` → 直接重置 `PENDING`，`retryCount=0`」。
  - **`[未实现]`** 幂等保障：无评论级去重主键，无 `(masterTaskId, link)` 唯一索引 → **会重复采集**。
- **FR-22** `[未实现]` 持久化已采集页数/cursor 以支持真正的断点续采。`SubTask` 无 `cursor` 字段。

### 3.7 多业务扩展

- **FR-23** `[已实现]` 系统设计为通用任务调度框架，评论采集是第一种功能实例（`featureCode=comment`）。
- **FR-24** `[部分实现]` 新增功能只需在数据库配置新的功能类型和供应商。
  - ⚠️ 前提是**该供应商已有实现类并注册为 Spring Bean**（见 §1.3 修订）。
- **FR-25** `[未实现]` 每个功能可定义自己的参数 Schema，提交时做动态 Schema 校验。

## 4. 非功能性需求

### 4.1 性能要求

| 指标 | v1.1 目标 | 测量方法 | 状态 |
|---|---|---|---|
| 并发提交任务数 | ≥ 500 TPS | JMeter/wrk 并发 POST `/api/collect/async`，持续 5 分钟，统计成功 TPS（MongoDB 本地副本集） | `[待确认]` |
| 子任务调度延迟 | P99 < 1s（不含供应商自身时延） | 从子任务置 `PENDING` 到置 `RUNNING` 的时间差分布 | `[待确认]` |
| 供应商频次控制精度 | 误差 ≤ 5% | 同一 providerKey 持续请求 10 分钟，实测 QPS 与 `ratePerSecond` 偏差 | `[待确认]` |

> **修订（C-07）**：v1.0 只写"≥500 TPS"未给口径。v1.1 补测量方法；未压测前不作为验收依据。
> **修订**：v1.0 的"误差 ≤5%" 与总体需求 v1.0 的"±10%"冲突 → **统一为 ≤5%**。

### 4.2 可用性

- `[待确认]` 服务自身可用性 ≥ 99.9%（需定义统计窗口与降级口径）。
- `[部分实现]` 供应商故障切换响应时间 < 30s —— 实现为**同步即时切换**（同一请求内遍历下一供应商），优于该指标；但"正在执行中"的任务无抢占机制。
- `[未实现]` 单点故障（数据库、Redis）通过主从/集群规避。

### 4.3 可扩展性

- `[部分实现]` 供应商、平台、功能可动态增减，无需停服（供应商变更需重新部署，配置变更无需）。
- `[未实现]` 调度器水平扩展（当前 JVM 单机内存队列 + 单机限流）。

### 4.4 可维护性

- `[部分实现]` 配置热加载（TTL 60s，**无管理后台接口**）。
- `[部分实现]` 监控与日志：Micrometer 指标已埋点（`task.submitted/completed/failed/queue.size`），
  **未暴露 Prometheus 端点**；无供应商 QPS / 错误率指标。
- `[部分实现]` 接口文档：已引入 springdoc-openapi，`OpenApiConfig` 文案误用为"舆情服务系统API"（需更正为评论采集服务）。

## 5. 架构设计概要

### 5.1 系统架构（v1.1 按实现重绘）

```
                       ┌──────────────────────────────┐
   调用方 ──HTTP──▶    │  CommentController  (/api/*) │
                       └──────────────┬───────────────┘
                                      │
                       ┌──────────────▼───────────────┐
                       │   CommentCollectionFacade     │
                       │  · 同步直采（doCollect）      │
                       │  · 异步队列（PBQ+线程池）     │
                       │  · aging / 公平配额           │
                       └───┬───────────┬───────────────┘
                           │           │
        ┌──────────────────▼──┐   ┌────▼─────────────────────┐
        │ DynamicProviderRouter│   │ RetryableProviderExecutor │
        │ · 候选顺序（不排序） │   │ · 指数退避 500ms×2^n      │
        │ · 限流 tryAcquire    │   │ · 失败抛出                │
        │ · 失败状态写入(死)   │   └────┬─────────────────────┘
        └──────────┬───────────┘        │
                   │                    ▼
        ┌──────────▼───────────┐  ┌──────────────────────────┐
        │ ProviderRateLimitMgr │  │ CommentProvider 实现类    │
        │ Guava RateLimiter    │  │ (Bean 名 = providerKey)   │
        │ 单机内存              │  │ 内部用 HttpUtil 调第三方  │
        └──────────────────────┘  └──────────────────────────┘

        ┌─────────────────────────────┐   ┌──────────────────────┐
        │ TaskManagementService       │   │ TaskRecoveryService  │
        │ · 建主任务/拆子任务 ✅       │   │ · 启动扫描 ✅         │
        │ · 状态更新方法【无调用方】❌ │   │ · 结果回写 ❌         │
        └──────────────┬──────────────┘   └──────────────────────┘
                       ▼
                 MongoDB（platform_feature_config / user_tier_config
                          supplier_state / master_task / sub_task）
```

> **修订（C-02/C-12/C-14）**：删除 Redis Sorted Set、分布式锁、`health-checker` 模块；
> v1.0 图中的"任务管理服务 / 配置管理服务"两个独立服务实际合并在同一进程内。

## 6. 数据库设计概要

> 详细字段定义见总体需求文档 §5。本节仅保留评论域视角。

| 集合 | 说明 | 关键字段 | 状态 |
|---|---|---|---|
| `platform_feature_config` | 平台功能定义 + **内嵌**供应商配置 | `platform_code`, `feature_code`, `providers[]` | `[已实现]` |
| `user_tier_config` | 用户等级与供应商偏好 | `tier_code`, `priority`, `feature_configs[].provider_order` | `[已实现]` |
| `supplier_state` | 供应商运行时状态 | `supplier_key`, `health_status`, `consecutive_failures` | `[部分实现]` 只写不读 |
| `master_task` | 主任务 | `id`, `status`, `links`, `total_links` | `[已实现]` |
| `sub_task` | 子任务 | `id`, `master_task_id`, `link`, `provider_key`, `status`, `retry_count`, `aging_count` | `[已实现]` |
| ~~`platform` / `function` / `supplier` / `user_priority`~~ | v1.0 的 4 张表 | — | `[已废弃]` |
| ~~`scheduler_config`~~ | 调度阈值配置 | — | `[未实现]` |

**关键设计思想（v1.1 修正）**

- 子任务优先级 = 用户等级 `priority`，**数值越小越优先**；aging 通过 `agingCount` 递减有效优先级。
- `supplier_state` 通过定时/失败回调更新，**但当前路由不读它** → 状态读写分裂，见 §3.1 FR-02 备注。
- 重启恢复：扫描 `master_task.status IN (PENDING, ACTIVE)` 与 `sub_task.status IN (PENDING, RUNNING, RETRYING)`，重置为 `PENDING`。

## 8. 关键流程

### 8.1 任务提交与路由流程（v1.1 修正）

`[已实现]` 用户提交请求 → 创建主任务（`PENDING`）→ 按 `links` 拆分 `sub_task`（`PENDING`）→ 返回 `masterTaskId`。
`[未实现]` 子任务入队 → 调度器拉取 → 分配供应商 → 执行 → 结果回写 → 主任务状态收敛。
**→ 后半段完全缺失，是当前最高优先级的功能缺口。**

`[已实现]`（同步路径）`POST /api/collect` → 直接在该请求线程内完成"候选供应商遍历 → 限流 → 重试 → 切换"→ 返回结果。

### 8.2 阈值与优先级动态调整流程

- `[部分实现]` 每个供应商维护本地队列长度指标 —— 实现为**按 `platform:feature` 维度的全局 pending 计数**，
  **不是按供应商维度**（与 v1.0 描述不符）。
- `[部分实现]` 调度器选择供应商时检查阈值 —— 仅在死代码 `route()` 中实现。
- `[部分实现]` 低优先级等待超时提升 —— 见 §3.3 FR-13 缺陷（优先队列不重排）。

### 8.3 健康检查与故障切换

- `[未实现]` 定期探活（v1.0 的 15s 探活）。
- `[部分实现]` 连续失败标记：`markProviderFailure` 会写 `supplier_state.health_status=DOWN`，但**无人读取**。
- `[已实现]` 路由从 `platform_feature_config.providers[].is_healthy` 读取剔除。
- `[未实现]` 自动恢复上线。
- `[部分实现]` 同供应商重试 `maxRetry` 次，仍失败则 fallback 至下一供应商。

### 8.4 重启恢复流程

- `[已实现]` `ApplicationReadyEvent` 触发 `TaskRecoveryService.scanAndRecover()`（**同步阻塞启动**）。
- `[已实现]` 查询 `master_task.status IN (PENDING, ACTIVE)` 及其下 `sub_task.status IN (PENDING, RUNNING, RETRYING)`。
- `[已实现]` 子任务状态重置为 `PENDING`，`retryCount = 0`。
- `[部分实现]` 重新入队 —— **结果无法回写**。
- `[未实现]` 确保不会重复创建主任务（无幂等键）。

## 9. 项目计划与里程碑

> v1.0 的 P0~P3 划分基于"从零开始"，与当前代码状态严重脱节（例如 P0 的"核心框架"已完成，
> 但 P1 的"用户优先级/阈值分流/恢复重启"声称完成而实际有阻断缺陷）。
> **v1.1 的里程碑以修复为主**，详见 `docs/plans/2026-09-23-defect-and-remediation-plan.md`。

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| P0 | 修复编译/启动/数据源 | `mvn clean package` 通过并成功启动 |
| P1 | 打通异步主链路（创建 → 执行 → 回写 → 查询可见） | 端到端用例通过 |
| P2 | 路由与调度正确性（排序、aging、阈值、公平配额） | 场景用例通过 |
| P3 | 可靠性与幂等 | 重启续采不重不漏 |
| P4 | 工程化（死代码、密钥、测试、分包收尾） | 无硬编码凭据、核心覆盖 ≥60% |
| P5 | 管理接口、鉴权、监控、集群化 | 见总体需求 §10 |

## 10. 风险评估

| 风险 | 影响 | 缓解措施 | 状态 |
|---|---|---|---|
| 供应商不稳定导致大量重试 | 任务积压、系统负载高 | 熔断 + fallback + 合理阈值 | `[部分实现]` 仅 fallback；熔断/阈值 `[未实现]` |
| MongoDB 单点性能瓶颈 | 任务读写慢 | 分片集群、读写分离、关键路径走 Redis | `[未实现]` 且当前**关键路径全部走 MongoDB** |
| 用户优先级频繁提升导致资源争抢 | 高低优用户感受趋同 | 控制提升比例和频次，监控 | `[未实现]` 无监控，且提升本身不生效 |
| 供应商频次控制不准 | 触发限流被禁 | 滑窗计数器 + 令牌桶，集群下 Redis 全局计数 | `[部分实现]` 单机令牌桶；集群方案 `[未实现]` |
| 多服务扩展参数校验复杂 | 开发成本高 | 定义 Schema 模板，JSON Schema 动态校验 | `[未实现]` 且当前**连基础参数校验都没有** |
