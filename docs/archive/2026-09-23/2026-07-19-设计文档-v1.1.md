## 1. 概述

构建一个多平台、多供应商的评论采集中间服务，支持动态配置供应商路由、任务优先级调度、防饥饿策略及断点续采能力。

### 核心目标与状态

| 目标 | 状态 |
|---|---|
| **多平台支持**：微博、抖音、小红书、B站、今日头条 | `[部分实现]`（微博 2 个供应商为 stub） |
| **多供应商路由**：同一平台功能可配置多个供应商 | `[部分实现]` |
| **动态配置**：功能、供应商、用户等级配置存 MongoDB，运行时调整 | `[部分实现]`（无刷新接口，TTL 60s） |
| **任务管理**：主任务/子任务两级模型，支持即时返回与异步模式 | `[部分实现]`（异步链路断裂） |
| **可靠性**：重试 + 供应商切换、健康检查、断点续采 | `[部分实现]`（重试判定错误、无健康检查、续采无回写） |

> **新增（v1.1）**：**当前代码不能编译、不能启动**（见 §12 G-01/G-02/G-03）。任何"实现现状"描述都以修复后预期为准，
> 但 §12 列出全部阻断项，必须先完成 P0 才能验证其余内容。

## 3. 数据模型设计

> ⚠️ **字段命名（v1.1 新增，关键）**：`MongoConfig` 对所有 `MongoTemplate` 设置了
> `SnakeCaseFieldNamingStrategy`，**落库字段名一律为下划线式**。
> 本节 JSON 使用**落库名**。任何手写 `Criteria`/`Update`/`@CompoundIndex` 必须使用下划线名，否则永不匹配（见 §6.2）。

### 3.1 PlatformFeatureConfig（集合 `platform_feature_config`）

```json
{
  "_id": "ObjectId",
  "platform_code": "weibo",
  "feature_code": "comment",
  "feature_name": "微博评论采集",
  "status": true,
  "providers": [
    {
      "provider_key": "weibo_official",
      "name": "微博官方接口",
      "rate_per_second": 2.0,
      "max_retry": 3,
      "priority": 10,
      "is_healthy": true
    },
    {
      "provider_key": "local_crawler",
      "name": "本地爬虫",
      "rate_per_second": 0.5,
      "max_retry": 5,
      "priority": 20,
      "is_healthy": true
    }
  ]
}
```

**字段语义**

| 字段 | 说明 |
|---|---|
| `provider_key` | 供应商唯一 Key，**必须与 Spring Bean 名称完全一致**；框架用 `ApplicationContext.getBean(key, CommentProvider.class)` 查找 |
| `rate_per_second` | 令牌桶速率（许可数/秒），直接来自供应商频次限制，不做换算。`1秒2次 → 2.0`，`2秒1次 → 0.5` |
| `max_retry` | 单供应商最大重试次数（首次调用不计入）。`0` = 不重试 |
| `priority` | 路由优先级，**数值越小越优先** |
| `is_healthy` | 健康状态，`false` 时被路由跳过。**由运维直接改 MongoDB**，无程序探活。TTL 60s 内生效 |

**索引**：`{ platform_code: 1, feature_code: 1 }` unique。

> `[缺陷]` 代码中 `@CompoundIndex(def = "{'platformCode': 1, 'featureCode': 1}")` 使用驼峰，与落库名不符。
> `[缺陷]` `providers` 数组顺序即候选顺序，代码**不排序**；必须保证写入时按 `priority` 升序（当前无任何保障）。
> v1.0 的 `thresholdConfig.{queueDepthThreshold, lowPriorityActivation}` **不存在**。

### 3.2 UserTierConfig（集合 `user_tier_config`）

```json
{
  "_id": "ObjectId",
  "tier_code": "VIP",
  "priority": 10,
  "description": "VIP用户",
  "feature_configs": [
    {
      "platform_code": "weibo",
      "feature_code": "comment",
      "provider_order": ["weibo_official", "local_crawler"],
      "activation_threshold": 0
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `tier_code` | 等级编码（`ENTERPRISE`/`VIP`/`NORMAL`），唯一索引 |
| `priority` | 调度优先级，**数值越小越优先** |
| `provider_order` | 该等级在此功能下的供应商起始顺序；未涵盖的供应商按全局顺序追加在后 |
| `activation_threshold` | 待处理任务数 `>=` 该值时，才允许启用偏好列表中第 2 个及以后的供应商；`0` = 始终全部可用 |

> `[缺陷]` `activation_threshold` 仅在死代码 `DynamicProviderRouter.route()` 中被读取，
> 门面实际调用的 `buildOrderedCandidates()` + `tryAcquireProvider()` 路径**完全忽略该阈值**。

**有效优先级计算（v1.1 修正）**

```java
public int getEffectivePriority() {
```

### 3.6 Comment（评论实体，v1.1 新增）

## 4. 核心流程设计

### 4.1 供应商路由流程（`[部分实现]`）

**门面实际路径（同步直采 + 异步执行共用）**

```
1. 取 PlatformFeatureConfig（平台+功能，走 Caffeine 缓存）
2. 若 request.specifiedProviderKey != null → 直接执行该供应商（短路，跳过 3~6）
3. 取 UserTierConfig 中该平台/功能的偏好 → buildOrderedCandidates() 构建候选顺序
   （偏好列表中的 key 按偏好序排在前面；其余按全局顺序追加在后）
   ⚠️ 不按 priority 排序，完全依赖 DB 数组物理顺序
4. 过滤 isHealthy == false
5. 遍历候选：
   a. tryAcquireProvider(platform, feature, key, ratePerSecond)   // 最长等待 500ms
      失败 → 跳过该供应商，继续下一个
   b. 执行（含重试）
   c. 成功 → 返回
   d. 失败 → 加入 excludedKeys，继续下一个
6. 全部失败 → 返回 "所有供应商均不可用"（不阻塞等待）
```

**`[缺陷]` 双实现分裂**：`DynamicProviderRouter.route()` 实现了另一套语义（含 `activationThreshold` 阈值判断），
但**没有任何调用方**，是死代码。两套实现导致"阈值分流"功能实际不可用。

**设计意图（本期目标）**：合并为单一路径 —— 由 Router 统一承担
「候选排序 → 健康过滤 → 阈值判断 → 限流 → 返回选中供应商」，Facade 只负责执行与切换。

### 4.2 重试与供应商切换（`[部分实现]`）

```
1. 选中供应商 A，RetryableProviderExecutor.execute(provider, request, maxRetry)
2. for (attempt = 0; attempt <= maxRetry; attempt++)
   a. attempt > 0 时先 Thread.sleep(500ms × 2^(attempt-1))
   b. provider.fetchComments(request)
   c. 成功 → 返回
   d. 异常 → 记录，继续
3. 全部失败 → 抛 RuntimeException（携带最后一次异常）
4. Facade 捕获异常 → excludedKeys.add(key) → markProviderFailure(...) → 返回 null → 外层切换供应商 B
5. 所有候选耗尽 → 返回失败
```

**`[缺陷]` 失败判定不完整（阻断级）**：`fetchComments` 的契约是"失败时抛异常"，
但**所有现有实现类在 HTTP 失败/解析失败时都是 `return STATUS_ERROR` 而不是抛异常**。
Facade 只捕获异常，因此：
- 不会重试；
- 不会切换供应商；
- 最终返回 `success=true` + 空列表。

**本期必须修复的口径**：`status != STATUS_SUCCESS` 一律视为失败。

### 4.3 防饥饿调度（`[部分实现]`，方向与 v1.0 相反）

**优先级队列排序（v1.1 实测）**

```java
// CommentCollectionFacade.PrioritizedTask#compareTo
@Override
public int compareTo(PrioritizedTask o) {
    return Integer.compare(this.effectivePriority, o.effectivePriority);  // 升序：小者先出
}

// 有效优先级
setAgingBoost(int boost) {
    this.effectivePriority = Math.max(0, basePriority - boost);   // 数值越小越优先
}
```

**Aging 机制实测**

```
aging 定时器：每 30s 扫描一次（首次延迟 30s）
对每个在队任务计算 elapsedSeconds = now - enqueueTime：
  · elapsedSeconds > maxWaitMinutes × 60 → effectivePriority = 0（最高优先级）
  · 否则 boosts = elapsedSeconds / agingIntervalSeconds
         expectedBoost = boosts × agingPriorityBoost
         若 expectedBoost > 当前 agingBoost → 提升
```

`[缺陷] validity`：`PriorityBlockingQueue` **仅在插入时堆化**，元素内部优先级字段变化后**不会重排**。
因此 aging 与 deadline 提升**实际不生效**（除非该元素恰好被重新插入）。
→ 本期方案三选一：(a) 出队时重算并回插；(b) 改用 `DelayQueue` + 动态延期；
(c) 取消 PBQ，改为每次调度时按 `effectivePriority` 从 DB 查询排序。

**公平配额（v1.0 语义 vs 实测）**

| 项 | v1.0 文档 | 实测 |
|---|---|---|
| 触发条件 | 高优先级（>80）占比超过 70% | `priority < 500` 占比 ≥ `fair-quota-threshold`(0.7) 且队列 > 5 |
| 批次大小 | `totalBatch × FAIR_QUOTA_RATIO` | `max(1, total × fairQuotaRatio)` |
| 状态 | 未描述 | 全局共享 `AtomicBoolean fairRoundActive` + `AtomicInteger fairRoundProcessed` |
| `[缺陷]` | — | 多消费者线程共享公平轮次状态会互相干扰；`500` 为无来源魔数 |

### 4.4 断点续采（`[部分实现]`，闭环断裂）

```
应用启动（ApplicationReadyEvent）：
1. TaskRecoveryService.scanAndRecover() 同步执行（大表会阻塞启动）
2. masterTaskRepository.findByStatus("ACTIVE") + addAll(findByStatus("PENDING"))
3. 对每个主任务：subTaskRepository.findByMasterTaskId(id)
4. status ∈ {PENDING, RUNNING, RETRYING} 的子任务：
   a. status = PENDING, retryCount = 0, nextExecuteTime = null
   b. 构造 CommentCollectRequest(platformCode, featureCode, targetId=从link提取, userId, userTierCode)
   c. collectionFacade.collectAsync(request)   ← 返回值被丢弃
   d. subTaskRepository.save(subTask)
5. 记录恢复日志
```

**`[缺陷]` 阻断级**：
- 提交的请求**不携带 `subTaskId`**，`CompletableFuture` 返回值被丢弃 → **执行结果永远无法回写 `sub_task`**，状态恒为 `PENDING`；
- `CommentCollectRequest` **没有 `url`/`link` 字段**，只传 `targetId`（从 link 末段提取）→ 采集目标信息丢失；
- `retryCount = 0` + 无幂等键 → 可能在重启前已部分采集后重复采集。

**本期方案**：让 `SubTask` 成为一等执行单元（`executeSubTask(subTaskId)`），
由调度器从 `sub_task` 表拉取 `PENDING` 记录执行并原子回写；恢复流程只负责置回 `PENDING`。

### 4.5 健康状态（v1.1 新增，`[缺陷]`）

当前存在**两套互不相通**的健康状态：

| 位置 | 写入方 | 读取方 |
|---|---|---|
| `platform_feature_config.providers[].is_healthy` | 运维手工改库 | `DynamicProviderRouter.buildOrderedCandidates` 后的 Facade 过滤 |
| `supplier_state.health_status` | `markProviderFailure()`（自动） | **无** |

→ 自动检测到的故障不会被路由感知；人工标记的故障不会被 `consecutive_failures` 统计。
**本期必须统一到一处**，并定义恢复条件（如"成功一次即恢复"或"冷却 N 秒后半开"）。

## 7. 供应商实现规范（v1.1 重写）

所有供应商必须实现 `CommentProvider`：

```java
public interface CommentProvider {
    /** 供应商唯一标识，与 Spring Bean 名称一致。 */
    String providerKey();

    /** 执行评论采集。失败时抛出异常，由上层执行器捕获并计入重试。 */
    CommonEntity<Comment> fetchComments(CommentCollectRequest request);
}
```

**实现约定**

1. **Bean 名称必须等于 `providerKey`**：`@Component("weibo_official")`。
   Facade 用 `applicationContext.getBean(key, CommentProvider.class)` 取得实例。
2. **HTTP 请求统一使用 `com.sysj.http.HttpUtil`**（`io.github.minghuo:http-client-utils`），
   **不得**自行 `new OkHttpClient` / `HttpClient` / `RestTemplate`。
   - 建议由 Spring 统一提供单例 `HttpUtil` Bean（超时、代理、连接池参数集中配置），
     而非每个 Provider 各自 `new HttpUtil.Builder().build()`（当前做法，`[缺陷]`）。
3. **失败必须体现在两个层面**：
   - 抛异常（网络异常、解析异常）；
   - 或返回 `CommonEntity.status = STATUS_ERROR`。
   两者都会被框架识别为失败（修复 G-02 后）。
4. **`request.getExtra()` 可能为 null**，取值前必须判空（当前直接 `.get()` → NPE，`[缺陷]`）。
5. **分页实现约定**：
   - golaxy 系列（B站/小红书）：游标 `cursor`，首页不传该参数（避免拼出 `cursor=null`）；
   - 抖音/头条：页码 `page`，从 1 开始；
   - 内部重试：参考 `auto-task-web` 的实现，**单个 HTTP 调用失败重试 3 次、间隔 1s**，
     与框架层的"供应商切换级重试"职责不同。
6. **密钥/地址不得硬编码在实现类或常量类中**，必须来自配置（`@Value` / `@ConfigurationProperties`），
   参考 `auto-task-web` 的 `GolaxyConstants.getCommentBaseUrl()` 做法。

## 8. 防饥饿策略详细设计（v1.1 修正方向）

### 8.1 优先级队列排序

```java
// 目标实现：数值越小越优先（与 priority 语义一致）
int compare(PrioritizedTask a, PrioritizedTask b) {
```

### 8.2 公平配额调度（v1.1 修正设计）

```java
// 目标设计：每个消费者线程本地计数，避免跨线程干扰

// "高优先级"的判定必须来自配置，而非硬编码 500
```

## 9. 限流模型

使用 Guava `RateLimiter` 令牌桶，按 `platformCode:featureCode:providerKey` 生成 key 管理独立限流器。

```java
private final ConcurrentHashMap<String, RateLimiter> limiters = new ConcurrentHashMap<>();

public boolean tryAcquire(String rateLimiterKey, double ratePerSecond, long timeoutMs) {
    RateLimiter limiter = limiters.computeIfAbsent(rateLimiterKey, k -> RateLimiter.create(ratePerSecond));
    return limiter.tryAcquire(timeoutMs, TimeUnit.MILLISECONDS);
}

public static String buildKey(String platformCode, String featureCode, String providerKey) {
    return platformCode + ":" + featureCode + ":" + providerKey;
}
```

- 令牌桶**懒创建**：首次 `tryAcquire` 时以 DB 配置的 `ratePerSecond` 初始化。
- 速率热更新：`syncRate(key, newRate)`；**当前无调用方**（缺管理接口）。
- 路由侧的等待时长为 **500ms**（v1.0 文档写 100ms）。

**`[未实现]` 集群一致性**：单机 JVM 内存限流，多实例部署时实际 QPS = 实例数 × 配置值。
集群方案（Redis 令牌桶 / 集中配额）列入 §12。

## 11. 验证方式

| 层 | 方式 |
|---|---|
| 编译 | `mvn -s <settings> clean package` 必须 0 error |
| 启动 | 默认 profile 下 `java -jar` 成功，`GET /api/health` 返回 200，日志无 SLF4J 绑定告警 |
| 单元 | `src/test` 下补充 JUnit5 测试（**注意：本沙箱 Mockito 不可用**，用真实对象 + 内存替身） |
| 集成 | 本地 MongoDB；提交异步任务 → 轮询直到终态；校验 `sub_task.result` 非空 |
| 恢复 | 任务执行中 kill -9 → 重启 → 校验任务继续且不重复 |
| 限流 | 对单供应商连续请求 10 分钟，校验实测 QPS 与 `ratePerSecond` 偏差 ≤5% |
| 防饥饿 | 灌入 1000 个低优 + 1000 个高优任务，校验低优任务在 aging 后确实被调度 |
