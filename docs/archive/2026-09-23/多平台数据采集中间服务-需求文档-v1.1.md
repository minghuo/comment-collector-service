## 1. 文档概述

### 1.1 项目背景

为满足业务对多社交平台数据的统一采集需求，构建一个中间服务层，屏蔽底层不同数据供应商（官方 API、第三方服务、自研爬虫）的差异，
提供统一的采集任务提交、调度、执行与结果返回能力，并支持动态配置供应商策略、优先级调度、失败重试及任务断点续采等高可用特性。

### 1.2 开发目标

- `[部分实现]` 实现多平台、多功能的统一任务入口，对外提供 RESTful API。
- `[部分实现]` 支持动态配置供应商及执行策略，无需重启服务即可调整优先级、频次、可用性。
  - 说明：配置存 MongoDB 并经 Caffeine 缓存（TTL 60s）；**当前缺少对外刷新接口**，新配置最长 60s 后生效。
- `[部分实现]` 实现灵活的任务路由与优先级调度，兼顾效率与公平，避免任务饥饿。
- `[部分实现]` 提供即时返回与异步任务两种模式。
- `[未实现]` 具备失败重试、供应商切换、任务持久化与重启恢复能力（骨架已存在，链路未打通，见 §12）。
- `[已实现]` 基于 **Spring Boot 3.4.5 + Java 21 + Spring Data MongoDB** 开发。

> **修订（R-01）**：v1.0 写"Spring Boot 3.2.5"，与 `pom.xml`（`3.4.5`）不符。
> **修订（R-24）**：原"保证高性能与水平扩展性"为无口径表述，本期明确为 §4 中可测量的指标。

### 3.2 供应商管理

- `[已实现]` 每个平台的同一功能可对应多个供应商（数据源）。
- `[已实现]` 供应商属性动态配置，字段如下：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `providerKey` | String | 是 | 供应商唯一标识，**必须与 Spring Bean 名称完全一致** |
| `name` | String | 否 | 展示名 |
| `ratePerSecond` | double | 是 | 令牌桶速率（**许可数/秒**，非"每 N 秒 M 次"） |
| `maxRetry` | int | 是 | 最大重试次数（首次调用不计入；`0` = 不重试） |
| `priority` | int | 是 | 路由优先级，**数值越小越优先** |
| `isHealthy` | boolean | 是 | 健康状态，`false` 时被路由跳过 |

> **修订（R-02）**：v1.0 写「数字越小优先级越高」，设计文档写「越高越优先」。**以本文档为准：数值越小越优先**（与实现一致）。
> **修订（R-04）**：v1.0 的 `rateLimit{maxRequests,perSeconds}` 结构已废弃，改为单一 `ratePerSecond`。
> 换算示例：`1秒2次 → 2.0`；`1秒3次 → 3.0`；`2秒1次 → 0.5`。

- `[已实现]` 供应商配置支持运行时动态加载与更新（MongoDB + Caffeine 缓存）。
- `[未实现]` 供应商实现类隔离 / 反射加载：v1.0 的 `implClass`（全限定类名反射实例化）已废弃，改为 **Spring Bean 名称查找**。
  新增供应商需要**编码 + 注册 Bean**，不是"只改配置不改代码"。
- `[未实现]` 健康检查机制：无程序探活。`isHealthy` 由运维直接修改 MongoDB 文档，缓存 TTL（60s）内自动生效。
- `[未实现]` 连续失败自动降级/恢复。

### 3.3 任务模型

#### 3.3.1 主任务（`master_task`）

由用户通过接口创建，一次请求可包含多个目标链接。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String | 主任务 ID，形如 `MT<epochMillis><8位UUID>` |
| `userId` | String | 用户 ID |
| `userTierCode` | String | 用户等级编码，决定调度优先级与起始供应商偏好 |
| `platformCode` / `featureCode` | String | 平台 / 功能 |
| `mode` | String | `SYNC` / `ASYNC` |
| `status` | String | 见 §5.6 状态机 |
| `links` | List&lt;String&gt; | 采集链接列表 |
| `requestParams` | String | 请求参数（JSON 字符串） |
| `supplierConstraint` | String | 供应商约束（可选） |
| `callbackUrl` | String | 回调地址 `[未实现]`（字段已存在但无消费方） |
| `totalLinks` / `successLinks` / `failedLinks` | int | 计数 |
| `createTime` / `startTime` / `completeTime` / `updateTime` | Instant | 时间戳（UTC） |

> **修订（R-09）**：v1.0 的 `totalSubTasks/completedSubTasks/failedSubTasks` 改名为 `totalLinks/successLinks/failedLinks`（与实现一致）。
> **修订（R-26）**：v1.0 未定义 `deadline`；设计文档定义了 `deadline`+`subTaskIds`。实现两者皆无 → 统一为**不存在**，防饥饿改用 §3.4.2 的 aging 机制。

#### 3.3.2 子任务（`sub_task`）

主任务按链接拆分为子任务，每个子任务对应一个链接。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String | 子任务 ID，形如 `ST<epochMillis><8位UUID>` |
| `masterTaskId` | String | 所属主任务 ID（**v1.1 统一命名**，v1.0 为 `mainTaskId`） |
| `link` | String | 采集链接（v1.0 写 `link`，设计文档写 `url` → **统一为 `link`**） |
| `providerKey` | String | 当前/已分配供应商（v1.0 为 `currentSupplier` → **统一**） |
| `status` | String | 见 §5.6 |
| `priority` | int | 基础优先级（继承用户等级；**数值越小越优先**） |
| `agingCount` | int | 等待轮次计数，用于动态提权 |
| `retryCount` | int | 当前供应商上的已重试次数 |
| `maxRetry` | int | 该供应商的最大重试次数 |
| `attemptedProviders` | String | 已尝试供应商（**JSON 数组字符串**；v1.0 定义为数组、设计文档定义为 `attemptedProviders[]`） |
| `result` / `errorMessage` | String | 执行结果 / 错误信息 |
| `nextExecuteTime` | Instant | 退避后的下次执行时间 |
| `createTime` / `startTime` / `completeTime` / `updateTime` | Instant | 时间戳 |

> **修订（R-19/R-20）**：`enqueueTime`、`lockOwner`、`lockExpireTime` 在实现中不存在 → 本期**从数据模型中移除**，锁机制列入 §12 差距清单。

### 3.4 供应商路由与调度

#### 3.4.1 优先级策略

- `[部分实现]` 默认按供应商配置的优先级从高到低选择（**数值小者优先**）。
  - 注意：当前实现**不对供应商列表排序**，直接按 MongoDB 文档中 `providers` 数组的物理顺序遍历。
    文档要求"按 `priority` 升序存储（写入时保证）"，但**没有任何代码保证或校验** → 属实现缺陷（C-17）。
- `[未实现]` 用户提交任务时可传入期望的起始优先级。
- `[部分实现]` 用户等级驱动起始供应商偏好：`user_tier_config.featureConfigs[].providerOrder` 为该等级用户的供应商顺序。
- `[部分实现]` 任务阈值触发：当功能待处理任务数 `>= activationThreshold` 时启用次优先供应商分流。
  - 该阈值定义在 `user_tier_config` 而非平台配置；且**在门面调用路径上未生效**（C-18）。
- `[部分实现]` 指标驱动指定：`CommentCollectRequest.specifiedProviderKey` 非空时跳过优先级路由。
- `[已实现]` 供应商不可用切换：`isHealthy=false` 时跳过，选择下一优先级供应商。

#### 3.4.2 公平调度与防饥饿

- `[部分实现]` 动态优先级提升（aging）：
  - 记录每个子任务进入待执行队列的时间；
  - 等待每超过 `collector.task.aging-interval-seconds`（默认 60s），有效优先级提升 `aging-priority-boost`（默认 10）；
  - **`agingCount` 直接按 `elapsed/interval × boost` 一次性计算，非阶梯累加**（v1.0 描述为"阶梯递增"）；
  - 超过 `collector.task.max-wait-minutes`（默认 30min）提升到最高优先级（0）。
  - **缺陷（C-08）**：`PriorityBlockingQueue` 在元素优先级变更后不会重排，aging/deadline 提升实际不生效。
- `[部分实现]` 公平配额：高优先级任务占比超过 `fair-quota-threshold` 时，按 `fair-quota-ratio` 分配处理能力给低优先级任务。
  - **缺陷（C-09）**：实现把"高优先级"硬编码为 `priority < 500`，该魔数无配置来源；公平轮次状态跨消费者线程共享，会互相干扰。
- **v1.1 明确**：v1.0「低优先级任务保证 30 分钟内一定被执行」是**不可保证的承诺**，改为
  「在系统负载允许时，低优先级任务的等待时间可通过 aging 机制收敛；不提供硬实时保证」。

### 3.5 任务执行与返回模式

- **即时返回模式（SYNC）**
  - `[已实现]` 适用于单个链接、供应商可同步快速返回的场景。
  - `[已实现]` 调用方接口直接等待，执行完成后立即返回结果。
  - **v1.1 修正**：v1.0「无需持久化子任务（但可选择性记录）」与实现不符 —— 实现中 SYNC 路径**不创建任何任务记录**。
- **异步任务模式（ASYNC）**
  - `[已实现]` 主任务创建后立即返回 `taskId`。
  - `[已实现]` 调用方通过任务 ID 轮询获取结果。
  - `[未实现]` 回调通知（`callbackUrl` 无消费方）。
  - `[未实现]` 后台异步调度子任务 —— **这是当前最大的功能缺口（C-13）**：异步任务只落库、不执行。

### 3.6 失败重试与供应商切换

- `[部分实现]` 子任务在某供应商执行失败后，若 `retryCount < maxRetry`，对该供应商重试。
- `[部分实现]` 达到最大重试次数仍失败，则切换到下一优先级可用供应商，并重置重试计数。
- `[部分实现]` 所有可用供应商均失败后标记最终失败，记录失败原因。
- **v1.1 新增失败判定口径（重要）**：供应商"失败"必须同时包含
  1. 抛出异常；**且**
  2. 返回 `CommonEntity.status != STATUS_SUCCESS`（即 `STATUS_ERROR`/`STATUS_PARAM`/`STATUS_URL_ERROR` 等）。
  当前实现只识别 (1)，(2) 被当作成功（C-06）。
- `[未实现]` 退避策略可配置。当前硬编码为 `500ms × 2^(n-1)`，且用 `Thread.sleep` 阻塞工作线程。

### 3.7 并发控制与频次管理

- `[已实现]` 供应商维度令牌桶限流，key = `platformCode:featureCode:providerKey`，速率取自 `ratePerSecond`。
- `[部分实现]` 无令牌时：当前实现为**等待 ≤500ms 后跳过该供应商**，不做排队。
- `[部分实现]` 多用户并发遵循优先级调度。
- **v1.1 明确范围**：限流为**单机内存实现**（Guava `RateLimiter`），集群部署下限流失效，需迁移到 Redis。集群方案 `[未实现]`。

### 3.8 持久化与故障恢复

- `[已实现]` 主任务、子任务、配置持久化至 MongoDB。
- `[部分实现]` 服务重启恢复：
  - 扫描 `master_task.status IN (PENDING, ACTIVE)`，及其下 `sub_task.status IN (PENDING, RUNNING, RETRYING)`；

  - **缺陷（C-14）**：恢复后提交的异步请求未携带 `subTaskId`，返回值被丢弃，**执行结果无法回写子任务**。
- `[未实现]` 心跳/锁机制：无 `lockOwner`/`lockExpireTime`，无锁过期回收。
- `[未实现]` 幂等保障：无 `(masterTaskId, link)` 唯一索引，无评论级去重主键。
- `[未实现]` 断点续采游标：`SubTask` 无 `cursor` 字段，恢复后从第一页重新采集。

### 5.6 统一状态机（v1.1 新增，替代三份文档的三套枚举）

**主任务 `master_task.status`**

```
PENDING ──(拆分完成/开始调度)──> ACTIVE ──(全部子任务终态)──> COMPLETED
   │                                │
   └──────────(创建即失败)──────────┴──> FAILED
```

| 状态 | 含义 |
|---|---|
| `PENDING` | 已创建，尚未进入调度 |
| `ACTIVE` | 有子任务在执行 |
| `COMPLETED` | 全部子任务成功 |
| `FAILED` | 存在失败子任务且无可重试供应商（`[未实现]` 部分成功状态） |

**子任务 `sub_task.status`**

```
PENDING ──> RUNNING ──> SUCCESS
   ▲           │
   │           └──(失败, retryCount<maxRetry)──> RETRYING ──> RUNNING
   │           │
   └──(切换供应商, 重置 retryCount)──────────────┘
               │
               └──(全部供应商耗尽)──> FAILED
```

| 状态 | 含义 |
|---|---|
| `PENDING` | 待执行 |
| `RUNNING` | 执行中 |
| `RETRYING` | 退避等待后重试（同供应商） |
| `SUCCESS` | 成功 |
| `FAILED` | 最终失败 |

> **修订（R-10）**：v1.0(docx) 用 `PARTIAL_SUCCESS/SUCCESS`，v1.0(.doc) 用 `PROCESSING`，设计文档用 `ACTIVE/COMPLETED`。
> **v1.1 以上表为准**。`PARTIAL_SUCCESS` 标 `[未实现]`。

## 7. 核心流程设计

### 7.1 主任务创建流程 `[部分实现]`

1. `[未实现]` 参数校验（平台/功能存在性、链接格式、返回模式合法性）—— 当前 `TaskSubmitRequest` 无任何约束注解，`@Valid` 形同虚设。
2. `[未实现]` 校验供应商可用性（至少一个启用供应商）。
3. `[已实现]` 生成主任务对象，`status=PENDING`，持久化。
4. `[已实现]` 按链接拆分为子任务，`status=PENDING`，批量插入。
5. `[未实现]` 主任务状态更新为 `ACTIVE`（**从未发生**）。
6. `[已实现]` 返回 `taskId`。
7. `[未实现]` **子任务由调度器异步消费执行** —— 缺口根因（C-13）。

### 7.2 供应商路由逻辑（子任务调度）`[未实现]`

调度器循环扫描 `sub_task` 中 `PENDING` 的子任务并分配供应商的流程**当前不存在**。
现存的是 `CommentCollectionFacade.doCollect` 的**同步直采路径**：

1. 取功能配置（含供应商列表）；
2. 若 `specifiedProviderKey` 非空 → 直接执行该供应商（短路，跳过路由）；
3. 加载用户等级偏好 → 构建候选顺序（**不排序**）；
4. 过滤 `isHealthy=false`；
5. 逐个候选：限流令牌（等待 ≤500ms）失败则跳过；
6. 执行（含重试）；失败则加入排除集合并继续下一个；
7. 全部失败 → 返回"所有供应商均不可用"（**不阻塞等待**，与设计文档 §4.1 第 8 步不符）。

### 7.3 子任务执行与重试 `[部分实现]`

- `[已实现]` 供应商通过 `ApplicationContext.getBean(providerKey, CommentProvider.class)` 取得并调用。
- `[已实现]` 成功 → 返回 `CommentCollectResult`。
- `[部分实现]` 失败重试（指数退避 500ms×2^n）+ 供应商切换。
- `[未实现]` 状态持久化（`TaskManagementService` 的状态更新方法**无任何调用方**）。
- `[未实现]` 主任务完成计数更新。

### 7.4 重启恢复流程 `[部分实现]`

1. `[已实现]` `ApplicationReadyEvent` 触发 `TaskRecoveryService.scanAndRecover()`（**同步执行，大表会阻塞启动**）。
2. `[已实现]` 扫描 `master_task.status IN (PENDING, ACTIVE)`。
3. `[已实现]` 扫描其下 `sub_task.status IN (PENDING, RUNNING, RETRYING)`。
4. `[已实现]` 一律重置为 `PENDING`、`retryCount=0`、`nextExecuteTime=null`。
5. `[部分实现]` 重新提交到异步队列 —— **但提交的是无 `subTaskId` 关联的请求，返回值被丢弃，结果无法回写**（C-14）。
6. `[已实现]` 记录恢复日志。

> 而第三阶段的"重启恢复"已有骨架）。v1.1 按**修复优先级**重排，详见配套的
> `docs/plans/2026-09-23-defect-and-remediation-plan.md`。

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **P0 可运行** | 修复编译失败、启动失败、依赖冲突、多数据源错配 | `mvn clean package` 通过；本地可启动并响应 `/api/health` |
| **P1 主链路** | 打通"异步任务 → 子任务 → 供应商执行 → 结果回写 → 查询可见" | 提交 3 链接异步任务，轮询可查到 3 条 SUCCESS 及评论内容 |
| **P2 调度正确性** | 路由唯一化、优先级排序、aging/deadline 生效、公平配额正确、阈值生效 | 单测 + 场景用例：低优任务在高优洪峰下仍被调度 |
| **P3 可靠性** | 幂等键、原子状态更新、退避可配置、重启恢复闭环、限流精度 | 重启后任务继续且不重复；压力下无丢失更新 |
| **P4 工程化** | 死代码清理、密钥外置、索引、分页、统一响应、单测覆盖 | 无硬编码凭据；核心类覆盖 ≥60% |
| **P5 生产就绪** | 管理接口、鉴权、监控暴露、集群化限流与调度 | 见 §12 |
